# ADR 0007 — 持久化的对话任务与中断语义

- 状态：已实现（任务 07，正常路径经真实端到端验证；故障/重启场景缺少自动化测试，见交付记录）
- 日期：2026-10-17
- 相关：[共享契约](../development/contracts.md) §5/§6、[任务 07](../development/tasks/07-durable-runs.md)、ADR 0005（执行追踪）、ADR 0006（持久化导入）

## 问题

在一次提问里，用户消息入库与“谁来执行这次运行”原本靠同一进程内的异步事件：消息提交成功之后，如果进程在事件被消费前退出，这次提问就永远不会执行，而数据库里已经有一条用户消息；反过来，接口返回“已受理”也可能只是意味着事件已经丢进内存队列。此外，重复的网络重试会再发一遍模型请求。

## 考虑过的方案

1. **继续用进程内事件 + 内存集合**：改动最小，但重启即丢失未开始的运行，且“已受理”不成立。否决。
2. **引入 Redis/Kafka/RabbitMQ 作为队列**：语义清晰，但要在已有 PostgreSQL 之外再引入一套必须运维的基础设施，且当前规模（单库、单进程 worker）不需要。否决。
3. **PostgreSQL 队列表 + 租约/fencing**：与导入任务（ADR 0006）用同一套已验证模式，事务边界天然覆盖“消息与任务同事务提交”，重启后仍可领取。**采纳**。

## 最终选择

- 队列表 `exobrain_chat_run_job` 与 05 的运行摘要（`exobrain_run`）一一对应；**与文件删除、文档导入两张队列各自独立**，不共用表。
- 提交事务：用户消息 + 固定历史/输入快照 + 排队任务在同一事务写入，返回 `runId` 与 `runStatus=QUEUED`；JVM 事件只用于尽快唤醒 worker，可靠性来自数据库。
- 幂等：`(actor, session, key)` 唯一约束，键由客户端对“一次新的提交意图”生成并在重试时复用；重复提交返回原来的 message/run（`idempotentReplay=true`），相同键不同内容按设计拒绝，不按问题文本去重。
- 领取与执行：短事务领取 + 租约 + fencing；模型与工具调用在事务之外；每个检查点续租；租约丢失的 worker 不能写回终态（`RunLeaseLostException`）。
- 授权：每次开始与关键步骤重新走 `ResourceAccess` 与运行守卫；账号停用、会话撤销、助手/知识库权限变化、模型停用都不会因为“已经入队”而绕过。
- 中断语义：不自动重放结果未知的外部调用；重启后先按租约超时把失联运行标为 `INTERRUPTED` 并保留已入库的消息与事件；`QUEUED` 可恢复。**明确不承诺 exactly-once，也不承诺任意步骤的无重复续跑。**

## 代价

- 多了一张队列表与一个后台 worker；运维需要理解 `app.runs.*` 的上限（并发、排队深度、每身份活动数、租约时长）与回滚时的“先停 worker、避免新旧 worker 双跑”。
- 排队任务与运行摘要必须保持一致：终态写入走 05 的幂等更新，不能出现两个“最终”状态。
- 数据库成为运行调度的单点；数据库不可用时不再降级为内存执行（这是刻意的取舍：宁可不接单，也不假装已受理）。

## 验证

- 已执行：默认单元 profile 269 通过 / 0 失败 / 4 跳过；真实 PostgreSQL 集成 38/38（03/05/06 的用例，未含 07 新增）；真实端到端账号/管理员 40/40 与游客 19/19，队列与运行记录均为 `SUCCEEDED`，应用日志 0 条 ERROR。
- **未执行**：幂等键重试、同会话并发提交、两 worker 竞争与租约过期、重启后领取/中断、取消与完成的竞争、多实例。这些场景目前只有代码与人工推理支撑，交付记录第 6 节逐条列出。

## 何时重新评估

- 需要跨进程/跨主机的高吞吐调度，或需要优先级与公平性时：重新评估引入专业消息中间件，并保留“提交与入队同事务”的语义。
- 需要步骤级恢复（真正续跑）时：必须为每个工具单独证明幂等键、结果查询或业务去重可用，不能统一重放。
- 若运行量增长到单库队列表成为瓶颈，应先测量领取延迟与队列表膨胀，再决定分区或外部队列。
