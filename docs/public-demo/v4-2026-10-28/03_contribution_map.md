## ExoBrain 基于什么项目，保留了哪些能力

上游是 JChatMind：一个 Java + Spring Boot + Spring AI 的 AI Agent 示例项目，前端为 React，数据库为
PostgreSQL 加 pgvector 向量扩展。本项目保留了这些核心能力：

- Agent 主循环：模型判断下一步 → 执行工具 → 读取工具结果 → 继续判断，直到交付答复或终止。
- 工具装配：助手配置里声明可用工具与知识库范围，运行时按配置装载。
- 会话与消息持久化：会话、消息、知识库、文档、片段都有独立数据表。
- SSE 状态推送：执行状态与回答通过 SSE 推送到页面。
- 基础 Markdown 解析与向量检索链路。

源码依据：上游 `README.md` 与本仓库的数据表建表脚本、Agent 工厂与消息服务。

## 哪些是「已实现」但不是「已验证」

- **多实例部署与网络分区**：代码按租约与 fencing 设计，但只在单机多进程与真实重启下演练过，
  没有做过跨主机、时钟漂移、网络分区的验证。
- **远端 CI**：工作流文件已提交，是否真实执行过要按流水线记录说明，不能用本机结果代替。
- **真实付费模型的效果对比**：只做过单一路径的连通与链路验证，没有做多模型效果与成本对比。

## 明确还没有做的

- **逐字流式输出**：当前回答由一次同步模型调用产生并通过工具参数交付，界面只有执行状态流，
  没有正文的增量推送。任何「打字机效果」都不是流式实现。
- **对外部调用的 exactly-once**：幂等只覆盖「同一会话的同一提交意图」，不覆盖模型或第三方服务。
- **管理员跨用户读取**：这是刻意不做的隔离，不是缺陷。
- **跨知识库的向量空间混用**：不同供应商或不同模型的向量不能混在一个索引里，换模型必须重新导入。

## 怎么核对这些说法

- 想看能力是否存在：对照上表「主要依据」的源码位置与当前仓库提交。
- 想看是否验证过：看对应的测试文件与运行记录，注意区分单元、集成与真实浏览器/生产证据。
- 想看边界：直接问「现在还做不到什么」，回答应当复述上两节的边界，而不是把计划中的能力当作已完成。

## 引用编号是怎么和来源对应的

编号一律由**服务端**生成，模型不自报编号，也不是检索排名或文档行号。系统有两条答复交付通道，
模型交给服务端的「来源身份」不同，编号的对应关系也就分两种说法。

### 通道一（旧协议）：模型填 `citationIds`

- 模型调用 `directAnswer` 工具，正文写在 `answer` 参数里，用到的来源 id 按顺序放进 `citationIds` 数组。
- 正文里的 `[n]` 对应**本次答复 `citationIds` 数组的第 n 项**（从 1 开始），不是检索排名、检索结果列表序号，也不是文档行号。
- 模型只负责从本轮检索命中里挑出实际用到的几条，把它们的 `citationId` 原样放进 `citationIds`；不能自己编造 id。
- 服务端按本轮真实检索结果校验这些 id（是否本轮命中、是否在授权范围内），再做去重与排序，最后把正文编号映射到展示用的最终编号。因此同一个来源在一次答复里只会出现一个编号。

### 通道二（新协议，本次公开体验使用）：模型逐条交「陈述 + 来源 + 原文短引」

- 模型调用 `groundedAnswer` 工具，**没有 `citationIds` 数组这个参数**；它逐条交付
  `statements`，每条包含三样东西：一句陈述、一个真实的 `citationId`、以及这段命中片段里的一段连续原文短引。
- 模型**完全不写编号**：正文里的 `[n]` 是服务端在读完全部陈述后按真实检索顺序排出来的，
  所以「第 n 项」指的是「服务端排出的第 n 个已核验来源」，而不是模型参数数组的第 n 项。
- 服务端除了校验 id 是否属于本轮真实检索、来源是否仍在授权范围，还要校验短引是否真的出现在
  **该条命中自己的片段**里；短引对不上就整轮判无效，不交付正文。
- 去重规则与旧协议相同：多条陈述指向同一来源时只保留一个编号，多条陈述共用这一个编号。
- 资料不足时走独立的「资料不足」结果：只说明缺什么，不挂任何引用，也不会为了凑引用挂不相关的来源。

### 两条通道共同的边界

- 点开来源能看到文档名、行号范围与原文片段；正文里写不出的行号不会出现在来源里。
- 这条契约只保证「来源身份与位置有效」，不保证「结论一定正确」——短引能对上只说明这句话确实在原文里，
  结论是否被原文支持、是否被过度概括，仍需人工读原文判断。
