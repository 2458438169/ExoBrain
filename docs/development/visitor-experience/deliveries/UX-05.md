# UX-05：真实首答测量与内容复核

日期：2026-10-19。对象：从 `2d5e96d` 导出的隔离候选，包含 UX-06 列出的独立修复。生产结果单列在 [UX-06](UX-06.md)，本页的本机数字不能代替公网性能。

## 结论

短答提示词、紧凑来源和真实等待状态已落地。最终资料上的 12 次真实运行全部进入 SUCCEEDED，但其中 Q05 混入工具协议残片，**原始内容验收为 11/12 可用**。修复后，HTTP 注入证明坏正文零落库，Q05 另用新意图真实复验通过；原失败样本保留，没有用重试覆盖。

剔除内容不合格的 Q05，原组 11 条可用答案的首次可见时间 p50 为 **6.145 s**、p95 为 **7.598 s**。这组达到本轮延迟目标，但只是有限串行样本。推荐第三题仍为 **556 字符**，未达到 200–350 字短答目标。没有实现逐字流式输出，也不以动画计算首答。

## 环境和方法

- 浏览器路径：Chromium → 真实 Nginx → 自有故障代理 → Java 21 应用 → PostgreSQL 17 / pgvector。测量时不启用故障注入。
- 真实生成模型：`DeepSeek-V4.1-Flash`，deepseek 协议；真实 Embedding：SiliconFlow `BAAI/bge-m3`，1024 维。调用的是与生产相同配置来源的服务，不是预置答案。
- 生成参数：temperature 0.2、topP 1.0、messageLength 16。四组均为同一个模型，不能称为多模型效果比较。
- 每组 12 问，每问建立新的提交意图；前三题实际点击首页入口，后续覆盖幂等、取消、重启、资料不足、资源权限、来源与许可。每个样本核对只有一条用户消息。
- 后两组问题间隔为 12 s；前两组短间隔。不是随机 A/B，不能把不同组的差值全部归因于提示词，更不能由恢复成功推断供应商限流原因。
- T_feedback 是点击到可见受理反馈；T_accepted 是点击到受理响应；T_first_answer 是真实答案正文首次出现；T_final_answer 还要求可确认终态。字符数按 Unicode code point 计算。
- 分位数采用 nearest rank `ceil(p*n)`。失败、超时及无效计时另记。未补造任务书建议的每版本 30 个样本。

## 逐组结果

| 组别 | 差异与样本量 | 运行成功 / 尝试 | 首答 p50 / p95 | 正文字符 p50 / p95 |
| --- | --- | --- | --- | --- |
| previous | 原提示词 + 原 v2 资料 | 4 / 12 | 8.234 / 10.796 s（仅 4 成功） | 739 / 1688 |
| candidate | 初版短答提示词 + 同一原 v2 | 7 / 12 | 6.366 / 7.000 s（仅 7 成功） | 385 / 644 |
| candidate-final | 加强简短分组 + 原 v2，间隔 12 s | 12 / 12 | 6.242 / 9.274 s | 327 / 550 |

最终原组的 T_feedback p50 / p95 = 5.6 / 7.9 ms，T_accepted = 136.4 / 203.8 ms，T_final_answer = 6.192 / 7.719 s。这些统计含已单列的 Q05 内容缺陷；内容合格口径为 11 个样本，首答 6.145 / 7.598 s。

前两组分别有 8 和 5 次快速模型调用失败。旧运行没有记录真实供应商 HTTP 状态，因此保留“模型调用失败、原因未充分归因”。单独 Python 探针曾收到 HTTP 403，但应用内连通检查成功，该探针不能代表 Java 请求链路。后两组成功也不能证明根因已消失。新增日志只记录数字 HTTP 状态码，不记录 URL、请求头或服务商正文。

`candidate-final` Q01 的一次非 JSON 详情读取使测量脚本中断，恢复后补记的 65.244 s 终态时间无效，已标记 `timingValidity.finalAnswer=false` 并从该项统计剔除；其 7.469 s 首答时间有效。没有删掉原值。

## 延迟分段与后续选择

模型调用仍是主要等待来源。Q05 新意图总首答 9.778 s，其中两次 MODEL_CALL 累计 8.566 s。RETRIEVAL 事件记录的是检索完成后的登记点，常为 0 ms，**不能解释为检索耗时为零**；检索调用的耗时在 KnowledgeTool 的 TOOL_CALL 事件里。一次提问也可能有多次检索，不把“一个意图”说成“一次模型请求”。

本轮先保留短答策略、真实已等待秒数、超过 10 s 的解释与停止入口，以及断线后的状态核对。若继续优化，优先扩大同模型、同语料、同间隔的质量样本并记录实际 HTTP 错误分布，再决定是否调整模型或检索调用；Q03 优先缩成三项代表改进。缓存和真正流式需要另行验证权限/索引版本、取消与最终提交协议，本轮没有顺手加入。
