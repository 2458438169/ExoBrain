## 一个被撤回的修复（重要）

先实现了一版「正文里的 `[n]` 必须落在 `1..已核验来源数` 之内，否则整轮判为无效」的守卫
（`AnswerFormatGuard.verify(answer, citationCount)`），单测 4/4 通过；但完整单元套件有 **2 个既有用例失败**：

- `JChatMindCitationTest.answerWithoutCitationIdsStillWorks`：`普通答复，数组元素 array[1]，选项 [2]。`
  这类正文里的方括号是数组下标/编号，不是引用，被误判。
- `JChatMindCitationTest.renumberingPreservesCodeLinksAndEscapedExamplesWithTheirOriginalOffsets`：
  代码、链接、转义示例里的 `[1]` 同理。

说明**纯文本规则无法区分「引用标记」与「正文里的方括号」**，会误杀正常答复，因此按既有产品行为撤回，
没有把它合进仓库（`-Punit` 回到 291 通过 / 4 跳过 / 0 失败）。真正可行的方向是**在 `directAnswer` 边界判定**：
模型交付答复时若正文含引用标记而 `citationIds` 为空或全部无效，就按无效交付处理；这需要一次明确的
协议决定与回归，不在本轮擅自加。

## 编号缺陷的修复（本提交）

先说清既有的部分，避免把别人的能力算成这次新增：`6774aee` 的 `AnswerCitationFormatter.relabel()`
**已经**在 `citationIds` 非空时把正文 `[n]` 按已核验来源重排，并在某个位置没有映射时抛
`Model answer references a source that could not be verified`。

真正的缺口是：**当模型没有给出（或给不出）任何可核验来源时，`relabel` 根本不会被调用，正文里的
`[1][2][3]` 就原样交付**。复跑里那 8 条就是这一类。

本提交补的就是这个缺口，且只用服务端已核验的事实判断：

- `AnswerFormatGuard.verify(answer, citationCount)`：正文里**真正像引用**的 `[n]` 必须落在
  `1..citationCount`（本轮已核验来源条数）内，否则整轮按无效交付处理（`INVALID_ANSWER_FORMAT`、零正文、不落库）。
- 抛出的异常文案与 `relabel` 保持一致（`Model answer references a source that could not be verified`），
  日志里能一眼区分「编号没有来源」与「工具参数残片」，不会互相冒充。两条都有单测断言文案。
- 判定会排除不是引用的方括号：围栏代码块、缩进代码块、行内代码、转义 `\[1]`、`[1](url)` 链接文本、
  `[1]: url` 链接定义，以及紧跟标识符的下标 `array[1]`。这几条都有单元测试守着。
- 保留既有语义：**正文不含编号**时，模型给了无效 `citationIds` 仍按原样「不生成引用、保留答复」
  （`fabricatedOrForeignIdsProduceNoCitations` 等 3 条既有用例不变）。

由此改动带来的**一处既有断言调整**（已在代码注释里写明理由）：
`JChatMindCitationTest.answerWithoutCitationIdsStillWorks` 的正文由 `…选项 [2]。` 改为 `…选项编号 2。`。
该用例的原意是「不传 citationIds 时答案照常保存 + 数组下标不被误判」，这两点都保留；
`选项 [2]` 在新语义下是一个没有来源的引用编号，属于本次要禁止的行为，因此正文措辞改掉，
同时新增 `citationMarkersWithoutSourcesNeverPersistAnAnswer` 显式测住「有编号无来源 → 不落库」。

验证：`-Punit` **297 通过 / 4 跳过 / 0 失败**（新增 `AnswerFormatGuardTest` 5 项 + 上面 1 项）。

## 阶段 2 补正与阶段 3 原型（2026-10-28）

上一轮把「未答上的旧问题」整条丢掉，虽然止住了串题，却让「把刚才的问题再答一次」失去指代对象。
这一轮把输入投影改成**按轮次、分主动/被动**，并落地了 grounded-v1 结构化交付原型。

### 1. 输入投影：未答上的旧轮是上下文，不是待办

`JChatMindFactory.project()`（`restoreMemory()` 保留为兼容入口）按「一条用户消息开启一轮」切分，然后：

| 轮次 | 处理 | 理由 |
| --- | --- | --- |
| 本轮（最后一条用户消息） | 保留，标记 `current-task` | 唯一执行意图 |
| 已答过的历史轮 | 整轮保留（用户消息 + 助手消息 + 工具响应，配对不变） | 正常多轮与显式追问 |
| 没答上的旧轮（失败/取消/中断） | 只保留那条用户消息，标 `previous-unanswered:context`；该轮的助手决策与工具结果全部丢弃 | 让「刚才那个问题」仍有指代对象，但旧来源不会冒充本轮来源 |

只要存在被动上下文，就在历史与本轮之间插入一条系统说明：历史里未完成的问题只是上下文，
不是本轮待办；只有当最后一条消息明确要求重答/继续时才回答它。

每次投影都写一条结构化日志（`model input projection: session=… trigger=… dbHistory=… projected=… decisions=…`），
只含消息 ID、角色、轮次与理由，不含正文：

- `current-task`：本轮任务；
- `answered-history`：已答过的历史；
- `previous-unanswered:context`：作为上下文保留的未答问题；
- `unanswered-round:dropped-with-tools`：因该轮未答上而被丢弃的助手/工具消息。

单测 `JChatMindFactoryMemoryTest` 覆盖 5 种情形：无关新问题、显式重试、正常多轮追问、
检索后整轮失败（工具与助手消息都不进投影）、取消/中断后的两类追问。

### 2. grounded-v1：陈述 + citationId + 原文短引

- `GroundedAnswerTool`（`groundedAnswer`）：模型交付 `statements[{text, citationId, evidenceQuote}]`
  或 `insufficient`，不写编号；
- `GroundedAnswerAssembler`：校验 `citationId` 必须是本轮登记过的命中，`evidenceQuote` 必须出现在
  该命中自身的完整片段里（空白归一后包含判断），复用 `CitationRegistry.resolve` 做授权、排序、去重，
  由服务端生成正文编号；
- `insufficient` 走独立结果：`本次可用资料不足以确认。` 加一句原因，不挂任何引用；
- 启用后 `directAnswer` 带引用会被拒绝（`INVALID_ANSWER_FORMAT`），不允许绕过短引校验；
  无来源的普通答复、旧协议的无引用路径、取消/租约/授权边界保持原样；
- 显式开关 `app.grounded-answer.enabled`（默认 false，环境变量 `APP_GROUNDED_ANSWER_ENABLED`），
  只在隔离环境打开；对应提示词 `docs/public-demo/v3-2026-10-28/agent-system-prompt-grounded.md`。

单测 5 条：服务端生成编号、短引跨片段被拒、编造或跨运行 id 被拒、资料不足无引用、
grounded 模式下 directAnswer 不得带引用。

### 7. 一个附带发现的配置问题：消息窗口把提问裁掉了

首次复跑时「把刚才的问题再答一次」仍然拿不到原问题。查投影日志发现：当时子 agent 的
`chatOptions.messageLength = 10`，而一轮带检索的问答会写入 11–12 条消息（用户、若干助手决策、
工具响应、最终回答、交付回执），于是**上一轮的提问本身落在窗口外**，窗口里只剩它的回答与工具结果。

两处处理：

1. 投影不再静默丢弃这类「没有归属轮次」的消息，而是记为
   `window-truncated:user-message-outside-window`（单测 `orphanAnswerOutsideWindowIsRecordedNotProjected`）；
2. 隔离实例把该 agent 的 `messageLength` 调到 40，保证一轮完整落在窗口内；本次对照就是在 40 下跑的。

这是**配置**问题而不是投影逻辑问题：窗口小于一轮所需条数时，任何投影都无法还原上一轮的提问。
产品侧是否需要按「轮」而不是按「条」裁剪窗口，需要单独评估，本轮未改默认值。
