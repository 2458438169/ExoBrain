## Q23 [fact] SUCCEEDED

**问**：为什么检查点要做有界等待，而不是一直等锁？

**期望**：['02_engineering_cases: 案例三（锁等待跨过租约期限会带病发请求）']（上限 350 字）

**尝试**：1 次 —— #1 SUCCEEDED/None modelCalls=2 wall=8162ms

**答**（297 字，1 条来源，编号 [1]）：

```
结论：因为一直等锁会拖住别的任务，还可能把仍在正常运行的运行误判成「中断」；有界等待是正确性与成本保护，不是吞吐优化。

- **一个锁等待会连累所有任务**：续期、心跳、写消息都是数据库写操作，若多个运行共用一个后台线程，一个任务卡在锁上就会饿住其他任务的心跳 [1]
- **被挡住时要能放弃**：执行检查点被锁挡住先在预算内重试，预算耗尽后用一次不加锁的读确认状态、fencing 和租约期限，确认不了就停止执行 [1]
- **代价是更早失败**：行锁冲突频繁时，运行会更快失败或降级为「中断」，而不是排队等更久；资料里有对应真实 PostgreSQL 用例，但没有给出吞吐数字 [1]
```

**来源 [1]** 02_engineering_cases.md L46-62

```
46| - **QUEUED（尚未开始）**：任务和用户消息已经持久化；服务重启后，worker 会重新领取尚未开始的排队任务。
47| - **RUNNING（已经开始）**：如果原 worker 因重启消失，租约过期后将运行记为 `INTERRUPTED / INTERRUPTED_BY_RESTART`。不自动重放结果未知的模型或工具调用，以免重复执行、重复计费。
48| - **已经登记取消**：如果运行仍在处理中且 `cancel_requested=true`，过期扫描将它记为 `CANCELLED / CANCELLED_BY_USER`，不能误标为重启中断。
49| - **已经完成**：取消请求不会撤销已经提交的完成终态；响应里的「已结束」不能解释成「取消成功」。
50| 
51| 上述状态转换已由真实 PostgreSQL 队列用例、独立 JVM 重启与 HTTP 取消演练核对。恢复指重新领取尚未开始的任务或读取已保存记录，不是从任意一次外部调用中间无重复续跑。
52| 
53| ## 案例三：一个任务的行锁，为什么会连累别的任务
54| 
55| **问题**：租约续期、心跳、写消息都是对数据库的写操作。当某一行被一条慢事务锁住时，续期会卡在锁上。
56| 如果多个运行共用同一个后台线程，一个任务的锁等待就会拖住所有任务的心跳，别的运行被误判成中断。
57| 
58| **方案**：把「锁等待」变成有界、可放弃的动作，并且每个运行独立。
59| 
60| - 每个租约使用自己的单线程调度器，心跳续期走独立连接 + 独立事务 + `SET LOCAL lock_timeout`，
61|   被锁挡住只会跳过这一拍，不会把运行判成租约丢失。
62| - 执行检查点如果被锁挡住，先在预算内重试；预算耗尽后用一次**不加锁的读**确认状态、fencing 与租约期限。
```

```
18| **验证结果**：真实 PostgreSQL 集成测试断言同键并发只产生一次运行、返回同一个 `runId`；同键不同内容返回冲突。
19| 真实浏览器里丢弃首个响应后手动重试，数据库仍然只有一个运行、一条用户消息、一次模型调用。
20| 
21| **边界**：这只保证「同一会话的同一提交意图最多执行一次」，不是对外部调用的 exactly-once 承诺。
22| 工具调用、模型请求本身仍然可能被重复发出，系统只保证结果写入与终态是唯一且受校验的。
```
