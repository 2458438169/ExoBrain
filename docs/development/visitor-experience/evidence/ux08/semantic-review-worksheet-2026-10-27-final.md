## Q06 [boundary] SUCCEEDED

**问**：网络不好，我重复点了发送，会运行两次吗？

**期望**：['02_engineering_cases: 案例一（幂等键，最多执行一次；不是外部调用 exactly-once）']（上限 350 字）

**尝试**：1 次 —— #1 SUCCEEDED/None modelCalls=2 wall=12202ms

**答**（233 字，2 条来源，编号 [1, 2]）：

```
不会：同一会话、同一提交意图最多执行一次。

- **去重机制**：服务端按 `(身份, 会话, 幂等键)` 去重，重试与重连复用同一个键；同一个键再次到达只返回原来的 `runId` 与状态，同键不同内容直接拒绝。实测丢弃首个响应再手动重试，库里仍然只有一个运行、一条用户消息、一次模型调用 [1]。
- **边界**：这不是对外部调用的 exactly-once 承诺 —— 工具调用与模型请求本身仍可能被重复发出，系统只保证结果写入与终态唯一且受校验 [2]。
```

**来源 [1]** 02_engineering_cases.md L8-22

```
8| **问题**：网络慢的时候用户会连点发送，或者请求其实已经到服务器但响应丢了。如果后端每收到一次就执行一次，
9| 会出现两条用户消息、两个模型调用、两笔费用，甚至两条不同的回答挂在同一个问题上。
10| 
11| **方案**：把「一次提问」变成带唯一键的提交意图，服务端按 `(身份, 会话, 幂等键)` 去重。
12| 
13| - 前端为每个「新的提问意图」生成一个键，重试与重连复用同一个键，只有用户明确问下一个问题才换键。
14| - 提交在一个事务里完成：写用户消息、固定历史快照、创建运行记录、入队。同一个键再次到达时不再新建运行，
15|   而是返回原来那次运行的 `runId` 与状态。
16| - 同一个键但内容不同则直接拒绝，避免拿旧结果冒充新请求。
17|

```

```
- **写答案要过 fencing**：领取任务会让 `fencing_token` 前进，写答案时必须同时满足「任务行仍是 RUNNING」和「fencing 未被接管」，答案与 `answer_message_id` 同事务写入，条件不满足就整笔回滚，迟到的内容一个字都不留 [1]。
```

## Q23 [fact] SUCCEEDED

**问**：为什么检查点要做有界等待，而不是一直等锁？

**期望**：['02_engineering_cases: 案例三（锁等待跨过租约期限会带病发请求）']（上限 350 字）

**尝试**：2 次 —— #1 FAILED/INVALID_ANSWER_FORMAT modelCalls=1 wall=6171ms；#2 SUCCEEDED/None modelCalls=2 wall=10235ms

**答**（288 字，2 条来源，编号 [1, 2]）：

```
因为检查点等锁等下去，会把「锁冲突」变成「租约过期而不自知」，代价更大。

- 检查点被锁挡住时先在预算内重试，预算耗尽后用一次不加锁的读确认状态、fencing 与租约期限；确认不了就停止执行，不再发起新的模型调用 [1]。
- 等锁的时间会与租约期限赛跑：真实 PostgreSQL 用例里，检查点在锁等待中租约到期必须抛出租约丢失 [1]。
- 这类设计是正确性与成本保护，不是吞吐优化；行锁冲突频繁时运行会更快失败或降级为「中断」，而不是排队更久 [1]。

边界：租约与 fencing 只在单机多进程与真实重启下演练过，跨主机、时钟漂移、网络分区没有验证 [2]。
```

```

47| - **RUNNING（已经开始）**：如果原 worker 因重启消失，租约过期后将运行记为 `INTERRUPTED / INTERRUPTED_BY_RESTART`。不自动重放结果未知的模型或工具调用，以免重复执行、重复计费。

53| ## 案例三：一个任务的行锁，为什么会连累别的任务
54| 
55| **问题**：租约续期、心跳、写消息都是对数据库的写操作。当某一行被一条慢事务锁住时，续期会卡在锁上。
56| 如果多个运行共用同一个后台线程，一个任务的锁等待就会拖住所有任务的心跳，别的运行被误判成中断。
57| 
58| **方案**：把「锁等待」变成有界、可放弃的动作，并且每个运行独立。
59| 
60| - 每个租约使用自己的单线程调度器，心跳续期走独立连接 + 独立事务 + `SET LOCAL lock_timeout`，
61|   被锁挡住只会跳过这一拍，不会把运行判成租约丢失。
62| - 执行检查点如果被锁挡住，先在预算内重试；预算耗尽后用一次**不加锁的读**确认状态、fencing 与租约期限。
```

## Q28 [rewrite] SUCCEEDED

**问**：重复提问会不会多花钱？

**期望**：['02_engineering_cases: 幂等提交，同键只执行一次']（上限 300 字）

**尝试**：1 次 —— #1 SUCCEEDED/None modelCalls=2 wall=12203ms

**答**（318 字，2 条来源，编号 [1, 2]）：

```
同一个问题重试或断线重连不会多跑一次，因此不会多出一笔模型调用和费用；但主动重新发送一个新问题就会重新执行、重新计费。

- 服务端按「身份 + 会话 + 幂等键」去重：前端为每个新的提问意图生成键，重试与重连复用同一个键，同键再次到达只返回原来那次运行的 `runId` 与状态，不新建运行 [1]。
- 真实浏览器里丢弃首个响应后手动重试，数据库仍只有一个运行、一条用户消息、一次模型调用；同键但内容不同会被直接拒绝，避免旧结果冒充新请求 [1]。
- 边界：这只保证「同一会话的同一提交意图最多执行一次」，不是对外部调用的 exactly-once 承诺，模型请求本身仍可能被重复发出，只有结果写入与终态是唯一且受校验的 [2]。
```
