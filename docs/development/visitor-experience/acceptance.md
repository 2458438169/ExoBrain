# 验收、性能测量与发布

本文件提供执行标准，不是已经通过的验收报告。开始前填写候选提交、前端构建、网关、资料、索引和模型配置版本。

## 1. 环境与证据

- 交互：真实 Chromium，至少 390×844 与 1366×900；320px、768px 做布局补充检查。
- 后端：真实 PostgreSQL + pgvector，使用隔离测试库。需要等锁、进程重启或响应丢失时，在隔离环境操作。
- 网关：请求穿过与候选发布配置对应的反向代理；不能只用 MockMvc 代表线上路由。
- 内容与性能：使用真实配置的模型/Embedding 服务，记录提供商与模型标识；密钥通过现有私密配置提供。
- 浏览器使用独立命名会话，结束时只关闭自己的会话，不干扰其他 agent 的浏览器或容器。

每个用例保留：ID、前置条件、动作、预期、实际、结果、证据文件。结果使用 `PASS / FAIL / NOT_RUN / ENV_BLOCKED`，不把未运行算成通过。故障夹具验证交互与持久化边界；真实问答验证实际回答体验，两者分别记录。

| ID | 场景与动作 | 通过条件 |
| --- | --- | --- |

| S02 | 对推荐入口快双击、连续按发送 | 不产生并行的相同意图 |
| S03 | 首条 POST 已到服务器但响应丢失，手动重试 | 同一幂等键、同一 runId、一条用户消息；草稿可恢复 |
| S04 | S03 成功后真正断开并恢复 SSE 连接 | 恢复历史/状态，不换新键自动再发送 |
| S05 | 同键重放已经成功、失败或取消的运行 | 输入可操作、终态明确，不永久停在生成中 |

| S07 | 取消排队任务、取消正在运行任务、取消与完成竞争 | 状态与后端一致；迟到答复不改写终态，不额外落库 |
| S08 | 等待期间编辑下一条草稿、快速切换会话 | 不误发草稿，旧响应不覆盖新会话 |
| R01 | 长回答配多个引用到达 | 答案开头可读；来源与过程默认紧凑，完整内容可展开 |
| R02 | 上滚、选择文字、展开来源时有新消息 | 保持阅读位置；可主动跳转到新回答开头 |
| R03 | 运行接口返回 HTML 404、JSON 404、500、断网 | 显示加载失败与重试，不误称未保存；已有数据不消失 |
| R04 | 历史确实缺少运行记录 | 有适当降级，提示每轮至多一次 |
| R05 | 打开只读示例并展开来源/过程 | 可阅读；无取消/续写副作用；亲自体验另建个人运行 |

| M02 | 手机软键盘开关、横竖屏切换 | 输入与发送/取消可达，内容和滚动不丢失 |
| M03 | 键盘操作与屏幕阅读标签检查 | 按钮有名称、焦点可见，抽屉关闭后焦点正确返回 |
| P01 | 等待过程中对照实际事件 | 显示真实阶段与等待时间，无虚构进度 |
| P02 | 开始下一轮时收到旧运行迟到事件 | 旧事件不激活终态、不覆盖当前运行 |

S03/S04 使用实际网络响应丢弃与连接中断验证，不能只给 DOM 派发一个 error 事件。数据库状态和模型调用观测用于核对，浏览器显示正确只是其中一部分证据。

## 3. 内容核对题组

由 UX-02 为每题登记事实依据与可接受回答边界。此题组用于体验验收，存放在验收目录，不上传到产品知识库，不修改既有冻结评测题集。

| ID | 问题方向 | 核对重点 |
| --- | --- | --- |
| Q01 | 用一句话和三个要点介绍 ExoBrain | 简短、用途清楚，指出可以亲自体验的能力 |
| Q02 | 这个项目的回答如何让我核对依据？ | 说明引用与原文，实际引用能打开并定位 |
| Q03 | 作者在原项目上新增了什么？ | 继承与新增分清，有证据，不编造个人履历 |
| Q04 | 网络不好重复点发送，会运行两次吗？ | 同键幂等的边界准确，不宣称任意调用 exactly-once |
| Q05 | 点击取消后模型迟到返回，会发生什么？ | 取消与正式结果写入的边界准确 |
| Q06 | 后端重启后任务会怎么样？ | 区分未开始的排队任务与结果未知的运行 |
| Q07 | 项目服务了多少客户、节省了多少成本？ | 无公开依据时不编造数字 |
| Q08 | 管理员能查看其他账号的私有知识库吗？ | 与当前资源隔离实现一致 |
| Q09 | 换一种说法询问引用或取消机制 | 能检索同一事实，不依赖背诵推荐问题 |
| Q10 | 现在是不是已经逐字流式输出？ | 按本次实际发布能力回答，区分状态 SSE 与正文流式 |
| Q11 | 有引用是不是就说明答案一定正确？ | 区分来源有效与答案事实正确 |
| Q12 | ExoBrain 基于什么项目，保留了哪些能力？ | 来源、许可与贡献边界一致 |

三个首页问题至少各真实执行一次，其余题覆盖主要边界。可以复用同一批性能问答中的结果，避免无必要地重复付费调用。

推荐问题的默认正文目标为约 200–350 个中文字符，超出时检查是否包含必要信息。用户主动要求详细说明、代码或长解释时允许更长；不能为了字数截断引用或牺牲正确性。

每条回答人工核对：结论有无依据、引用是否实际支持结论、是否遗漏关键边界、是否出现过期描述。正确的来源 ID 不代替事实核对。

<a id="performance"></a>
## 4. 性能测量

### 时间点与口径

| 指标 | 定义 |
| --- | --- |
| T_feedback | 点击到按钮/页面出现受理反馈；不包含模型内容 |
| T_accepted | 点击到收到消息受理响应 |
| T_first_answer | 点击到真实最终答案正文首次可见；不把思考状态、工具 JSON 或占位文案计入 |
| T_final_answer | 点击到完整答复可读且运行结束状态可确认 |
| T_queue / T_model / T_retrieval | 服务端记录的对应阶段，用于归因，不能与浏览器总时长混算 |
| answer_chars / source_count | 正文字符数和实际引用条目数，统计方式在两侧保持一致 |

当前非流式模式下，T_first_answer 与正文完成时间可能接近，这是实际结果，不能通过播放动画制造差值。

### 测量安排

1. 固定同一版 v2 语料、同一题组、模型和可比的网络环境，分别测优化前与候选版本。一次最多比较一个明确策略。
2. 从题组中选择 10 个代表问题，每题独立执行 3 次，得到每个版本 30 个样本；质量核对可复用这些结果。
3. 使用新的发送意图测实际执行。幂等重放不计为新的模型性能样本；缓存是否开启、冷/热状态分组报告。
4. 每个样本记录运行结果、上述时间、重试次数、用量、模型配置、资料/索引版本。失败与超时保留，不能只挑成功的最快结果。
5. 若条件只允许较少调用，报告实际 n、原始样本与限制，不补足虚构样本。30 个样本的 p95 也只是有限样本估计，不能宣传成生产 SLA。

### 目标分级

| 要求 | 判定方式 |
| --- | --- |
| 点击后立即有 UI 反馈 | 目标约 200ms 内，不需要等模型；本机浏览器记录 |
| 进度与终态真实 | 硬要求，对照服务器事件与实际运行 |
| 超过 10 秒等待可理解、可操作 | 硬要求，显示实际等待及取消/恢复入口 |
| 推荐短问答 T_first_answer p50 ≤ 10s、p95 ≤ 20s | 优化目标，报告是否达到及分段原因 |
| 质量、引用和幂等不回退 | 硬要求，以功能矩阵与内容核对为准 |

外部服务不可用时标注 ENV_BLOCKED，保留错误与范围。至少三个入口的真实端到端问答是体验发布的必要证据；完整性能目标未达到时可以单独列为后续优化，但不得把该项标为已达标。

## 5. 工程检查

在候选源码根目录使用项目已有检查入口。数据库配置按当前隔离环境设置，不把生产数据库作为测试目标。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check.ps1 -Unit
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check.ps1 -PostgresIt -RequireDatabase
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check.ps1 -Frontend -Build
python evaluation/scripts/validate.py --dataset evaluation/datasets/questions-v1.jsonl --corpus-manifest evaluation/corpus/v1-2026-10-14/manifest.json --freeze evaluation/datasets/freeze.json
python -m pytest evaluation/tests -q
```

使用环境中可用的正确 Python 解释器。前端脚本已经生成 `dist-public` 与 `dist-admin`，不是虚构的 `npm run build:demo` 命令。

每个任务先跑与改动相关的检查；集成后对最终候选跑完整组合。纯间距和文案不新增镜像实现的单元测试，浏览器截图与操作验证即可。状态机、权限投影、关联、幂等或流式协议变更需要针对其语义补回归。

最近 R5 报告中的 271 个单元与 63 个 PG 用例是历史数量，不能原样填入新报告。新报告读取当前结果，分别列通过、失败、错误、跳过与原因。GitHub Actions 是否真实执行另列，不用本机结果冒充。

## 6. 发布顺序与回退

### 发布前

1. 明确最终代码提交，所有被打包文件都可追溯。核对未提交 UI 的合并范围，不夹带 `ui/preview.html`。
2. 记录当前线上镜像、前端 current、网关 hash、公开 Agent/KB/示例配置和索引版本。
3. 备份实际即将变化的内容及数据库/文档，验证备份可读取。保留旧前端资源、旧镜像、旧配置与旧索引引用。
4. 在隔离环境用同一发布包完成验收，准备完整的 release manifest 和回退指令。

切换前检查活动公开运行，优先等正在处理的问答收尾再更改 Agent 配置；不以删除任务或清空队列作为发布前提。必要重启产生的中断按现有持久任务语义记录。

### 应用顺序

1. 提前准备并验证新版资料、候选 KB 与索引；此时旧演示继续服务。
2. 发布兼容的运行关联接口与精确网关规则，执行配置语法和实际路径检查。
3. 发布对应的游客与账号前端构建，确认资源路径和浏览器加载的资源指纹。
4. 切入已验证的新 KB、提示词与公开范围，保持公开 Agent ID。配置需要重启时合并安排并检查真实生效值。
5. 发布经审核的真实只读示例，检查新旧引用可读。
6. 用全新游客做三个推荐问题的线上抽样，验证运行详情、来源定位、刷新和输入恢复。再检查旧示例、账号入口与匿名权限边界。

正常情况下不在生产注入长行锁、杀 JVM 或做批量模型压测。此类边界在隔离验收中完成，线上只做适量真实使用验证。

### 回退原则

| 失败层 | 回退对象 |
| --- | --- |
| 新前端不可用 | 恢复前端 current/资源版本，保留兼容后端 |
| 网关规则有问题 | 恢复对应配置，语法验证后 reload |
| 新版数据或检索效果错误 | 恢复旧 allowedKbs、提示词和公开配置；新库暂不参与服务 |
| 新后端异常 | 恢复上一个已核对镜像及与其兼容的配置 |

普通版本回退不需要清空数据库、删除聊天或回删业务表。不要用很早的备份覆盖期间合法新增的数据；若真的需要数据恢复，应单独分析具体损坏范围。
