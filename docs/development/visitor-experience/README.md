# ExoBrain 简历链接访客体验优化方案

版本：2026-10-19。方案基线：`09e9982aa4a2678b913ef6889fce1c73aa4f88ef`。状态：**UX-01–04 已实施，独立验收与 UX-05/06 记录已补齐；实际发布结果以 UX-06 为准**。

本方案面向从简历打开 https://exobrain.sharmoon.cc.cd/ 的首次访客。交付目标是让对方无需登录、无需了解 Agent 术语，完成一次「提问 → 读懂答案 → 核对原文 → 继续追问」的体验，并能了解项目新增能力与技术取舍。

本目录保留最初任务书和线上基线，也记录后续实施与独立验收。[UX-05](deliveries/UX-05.md) 给出真实内容/耗时样本，[UX-06](deliveries/UX-06.md) 给出问题修复、功能矩阵、发布及回退结果。下文“目标”“要求”和基线观察属于方案口径，不能代替实际测量。

## 2. 实施前基线：为什么这一轮优先做

2026-10-19 使用独立 Chromium 游客身份体验了首页推荐问题。以下是一次真实问答的观察，不能作为总体性能分位数。

| 编号 | 已观察或已核对的事实 | 用户感受到的问题 |
| --- | --- | --- |
| E01 | 点击推荐卡片只填入输入框，还要再次点击发送；首次进入默认展示空的「我的记录」 | 第一步不够直接，空状态占据较多空间 |
| E02 | 从点击发送到最终正文首次出现为 19.752 秒；最终正文 1,655 字符 | 等待较长，完成后阅读负担也大 |
| E03 | 正文后有 6 条展开的来源片段，完成时视口自动滚到来源底部 | 答案开头被带出视野 |
| E04 | 游客会话运行列表多次返回 Nginx HTML 404；页面显示「此记录未保存执行详情」 | 接口故障被解释成没有记录，执行追踪不可体验 |
| E05 | 打开来源提示「旧版索引」「没有精确位置」，只能打开整篇文档 | 点击引用后仍需自己寻找证据 |
| E06 | 公开资料仍以 2026-10-14 为核对日期，将正文索引、结构化来源列为后续方向 | 回答遗漏已经完成的新能力 |
| E07 | 390×844 首页第三张卡片在折叠区域之外；页宽正常，为 390px | 移动端首屏还可以更聚焦 |

进一步只读核对得到：

- 线上有效配置为 `/etc/nginx/sites-available/exobrain`，由 `sites-enabled/exobrain` 启用；其公开路径白名单缺少运行列表、运行详情和导入状态路径。
- 仓库 [deploy/nginx.conf](../../../deploy/nginx.conf) 已包含这三类 GET 路径，说明存在部署配置差异。
- 取消接口已存在于后端，但当前仓库模板和线上白名单均没有放行对应的游客取消路径；这一点来自配置/代码核对，本轮未在线提交取消请求。
- `RunViews.PublicSummary` 当前不含触发消息和答案消息的关联 ID；仅修网关，还不足以保证游客刷新后能把无答案运行准确挂回原问题。
- 冻结测试 `test_public_demo_sources_are_byte_identical` 要求旧版公开资料与评测快照逐字节相同。直接重写那三份旧文件会破坏原有评测。

## 3. 目标体验

### 首次打开

主文案建议为「问一个问题，查看答案背后的原文」。副文案用一行解释 ExoBrain 的用途，技术栈与个人贡献放在可继续探索的位置。

手机首屏能看到一个主行动按钮与可直接点击的问题。桌面保留侧栏能力，首次无历史时优先呈现体验入口；有历史的访客仍容易返回自己的记录。

### 第一条问题

推荐入口直接创建发送意图并提交，点击后立即有反馈。沿用同一套消息提交、幂等和失败恢复逻辑，不能另写一套「演示专用快捷发送」。

首批建议保留三个具体问题：

| 展示文案 | 要验证的能力 | 推荐问题方向 |
| --- | --- | --- |
| 30 秒了解这个项目 | 简短、可核对的项目介绍 | 用一句话和三个要点说明用途，并指出可以亲自体验的能力 |
| 看一条有原文出处的回答 | 检索和引用定位 | 针对新版公开资料中的一个具体问题回答，引用应能定位到支持结论的段落 |
| 作者新增了哪些能力 | 贡献与工程取舍 | 区分上游继承与本仓库新增，选择三个有公开证据的改进 |

问题与资料内容须一起审核。第二个问题的最终措辞由 UX-02 和 UX-03 对齐，不能依赖未上传的材料。访客仍可自由输入其他问题。

### 等待、阅读和继续

1. 点击立即显示受理中的状态，随后依据实际事件展示分析、检索或整理回答。
2. 默认首答采用「一句结论 + 最多三个要点」，推荐问题的正文以约 200–350 个中文字符为内容目标。
3. 来源默认是紧凑入口，能展开全部证据；点击一条引用打开原文并定位。
4. 一轮工具调用归入一个可展开的执行过程。失败、取消和中断仍在主视图中清楚可见。
5. 回答到达后，访客能从答案开头阅读；正在读旧内容时不会被抢走滚动位置。
6. 答案下提供至多两个相关追问。选择追问才发起新的运行。

### 页面结构参考

以下只规定信息层次，颜色、组件和字体沿用已接收的主题。手机上的推荐问题采用紧凑按钮，避免每个入口都占一张大卡片。

```text
ExoBrain                                      我的记录

问一个问题，查看答案背后的原文
检索公开资料，阅读结论，点击出处核对。

[30 秒了解这个项目 →]
[看一条有原文出处的回答 →]
[作者新增了哪些能力 →]

查看真实示例                       浏览公开资料

[输入你的问题……                         发送]
```

回答完成后的主列结构：

```text
你的问题

一句话结论
• 重点一
• 重点二
• 重点三

来源：项目导览 · 工程案例        展开全部依据
已完成 · <实际耗时>              查看执行过程

[相关追问一] [相关追问二]
```

这里的文本结构是生成与展示目标，不是预置答案。运行期间在答案位置显示真实状态和取消操作；失败时显示原因及恢复操作，不用成功样式遮盖失败。

## 4. 交付分层

### 第一批：接通功能与完成体验闭环

必须交付 UX-01、UX-02、UX-03、UX-04，以及 UX-05 中的真实状态反馈、计时基线与低风险优化，最后通过 UX-06。

这一批完整发布后，新游客应实际体验到运行详情、精确引用和短答案。编译通过、截图好看或只更新 README 都不能替代这条线上路径。

### 第二批：根据数据决定的性能增强

真实 token 流式输出、检索缓存或模型切换属于 UX-05 的后续候选。先测量并证明收益，再决定落地范围。当前后端用同步模型调用和完整的 `directAnswer` 工具参数交付答案，不能用前端打字动画冒充首字加速。

涉及流式输出时必须补齐取消、租约丢失、部分结果与最终提交的协议，保留 R1–R5 的执行边界。详见 [共享契约](contracts.md#streaming)。

- UX-02：新版本公开资料、资料清单、演示提示词、README/架构/归属说明、数据发布脚本、`.gitattributes` 的新增规则。
- UX-03/04：共享一个前端负责人，负责 `AgentChatView`、`AgentChatHistory`、`EmptyAgentChatView`、引用预览、输入组件及相关 API/types/hooks。
- UX-05：先做测量；后端优化只修改自己明确领取的文件。前端与提示词改动交回其负责人集成。
- UX-06：验收脚本和发布证据；发现产品问题回到相应任务，不在验收阶段悄悄另改一套产品逻辑。

## 6. 现场约束

方案编写时，主仓库在 `D:/Code/Java/JChatMind`，分支 main，HEAD 为上述基线。另有 **19 个已跟踪 UI 文件改动与未跟踪的 `ui/preview.html`**。其中包含其他 agent 的主题工作和此前发送/展示修复，不能把它们视为可丢弃的临时内容。

实施前记录新的 HEAD 和文件状态。优先使用各自工作树；前端负责人明确接收既有 UI 补丁后再继续改。不要用重置、清理、整树格式化或全量暂存来解决协作冲突。`ui/preview.html` 不属于本方案交付。

本仓库的项目远端是 `exobrain`，`origin` 是上游 JChatMind。需要推送时核对目标，保留上游来源与许可。

最近的后端发布基线为 R5 修复；本次只读核对的前端仍指向 `/opt/exobrain/releases/20261018-durable-runs`。最终验收必须记录实际部署的前端、后端、网关、资料和索引版本，不能把工作区测试结果直接算作线上结果。

## 7. 完成的定义

- 使用全新游客身份，在 390px 手机视口与桌面完成三个推荐问题的体验。
- 新演示回答能核对来源位置，运行详情能读取；取消、断线重连、刷新和受理响应丢失不产生重复消息或错误终态。
- 首答和失败状态可读，引用与执行过程可展开，读旧内容时不会自动跳到底部。
- 新资料能准确说明个人贡献，旧冻结评测保持可复现。
- 使用真实服务完成约定的体验抽样，按实测写性能和质量结论；环境阻碍单列。
- 发布来自明确提交和数据清单，线上冒烟覆盖真实新提问，而不仅是健康页与公开列表。

每项任务交付「改了什么、提交 SHA、如何验证、证据位置、已知限制、下一项所需输入」。具体判定以 [验收与发布](acceptance.md) 为准。
