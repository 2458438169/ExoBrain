# 共享契约

本文件约束 UX-01 至 UX-06 的交接。它补充 [现有工程契约](../contracts.md)，不改变既有租约、权限和引用核验语义。下文标为「新增要求」的部分尚未实现。

<a id="api"></a>
## 1. 公共入口与请求语义

游客构建使用 `/api/demo` 与 `/sse/demo`；账号构建使用 `/admin/api` 与 `/admin/sse`，由网关映射到后端账号路径。

| 方法与游客路径 | 职责 | 所有权/发布约束 |
| --- | --- | --- |
| `GET /api/demo/chat-sessions/{sessionId}/runs` | 列出会话运行 | 自己的会话，或已发布的只读示例 |
| `GET /api/demo/runs/{runId}` | 读取运行与事件 | 与所属会话同一授权范围 |
| `POST /api/demo/runs/{runId}/cancel` | 请求取消 | 仅当前游客自己的可操作运行；公开示例不能取消 |
| `GET /api/demo/documents/{documentId}/ingestion` | 读取导入状态 | 当前有权读取的公开文档 |
| `GET /api/demo/documents/{documentId}/content` | 读取引用原文 | 当前有权读取的公开文档 |

保留既有聊天、目录、示例和 SSE 路由。公开路径保持精确白名单；不能为解决 404 而透传全部管理接口。请求方法由网关规则与后端共同正确处理，读取行为不产生写入副作用。

后端继续使用 `ApiResponse { code, message, data }`。`http.ts` 已解包 `data`，前端调用 `listSessionRuns()` 得到的是 `{ runs }`，不是再次带 `data` 的对象。HTML 404、无法解析的 200 响应与 JSON 业务错误都属于读取失败。

<a id="run-association"></a>
## 2. 运行与消息关联

### 当前事实

- 账号运行摘要有 `triggeringMessageId`、`answerMessageId`。
- 当前游客 `RunViews.PublicSummary` 不含这两个字段。
- `runId` 在部分消息 metadata 中存在，但不能假定每一条旧消息或用户消息都有它。

### 新增要求：仅向会话所有者补充关联

访客确实拥有会话时，运行摘要返回其触发消息 ID 和可空答案消息 ID。两者指向同一份已授权历史中可见的消息。公开示例仍使用既有受限投影，不改成账号完整投影。

前端已有可选字段可承接此增量；后端可以通过明确的自身会话投影实现。若采用可空字段，公开示例不得填入不属于其公开数据契约的值。任何修改都要测试自己、另一游客、公开示例和账号运行四种范围。

关联优先级：服务端 `answerMessageId` / `triggeringMessageId` → 经核对的消息 `metadata.runId`。没有可靠关联时保留独立运行/历史展示，不按消息内容、时间相近或数组下标配对。

一轮执行只显示一个运行摘要。答案不存在时，失败、取消、中断和活动状态挂在触发问题下方。对于公开示例，无法关联的过程可以单独呈现，不能伪造某个答案与运行的关系。

<a id="load-state"></a>
## 3. 读取状态

前端建议使用独立的 `idle / loading / ready / error` 状态，数据与请求结果分开保存。

| 情况 | 应显示 |
| --- | --- |
| 首次未完成读取 | 正在读取执行记录 |
| 成功取得摘要/详情 | 真实数据 |
| 成功空列表，且消息确实属于缺少记录的旧历史 | 简短的历史记录说明 |
| 404 / 500 / 网络失败 / 响应格式错误 | 暂时无法读取，提供重试 |
| 已有数据，后台刷新失败 | 保留已有数据，说明状态尚未更新 |
| 切换会话后旧请求返回 | 丢弃旧响应，不更新当前视图 |

只有成功的空结果才允许进入「没有记录」。如果消息已经带 runId，但列表或详情未取得该记录，应呈现未能取得数据的状态，不直接判定为旧历史。

`getRun` 的一次失败不能永久阻止重试。自动轮询仅用于可见页面的活动运行，默认沿用约 5 秒间隔；同一会话同类请求避免重叠，终态停止。取消请求后可立即刷新一次状态。

<a id="submission"></a>
## 4. 发送意图与恢复

首页推荐、手动输入、示例复用和追问使用一个协调入口。一个发送意图包含固定的 session、agent、规范化后的内容与一次生成的 `idempotencyKey`。

| 状态 | 键与行为 |
| --- | --- |
| 用户明确开始新问题 | 生成一个新键 |
| 发送正在进行 | 禁止并行重复提交同一意图 |
| 请求失败、响应丢失、连接状态未知 | 保留原内容和原键；重试复用 |
| 服务端确认受理或同键重放 | 统一收尾并保存 runId，清理首条自动发送标记 |
| SSE 重连 | 恢复历史与运行状态，不能生成新键重发已受理问题 |
| 重放返回终态 | 立即结束等待并恢复操作，不等待一个不会再来的 AI_DONE |
| 用户明确选择重新提问/重新执行 | 是新的意图，使用新键；与「重试提交」区分 |

必须保留此前修复的 `pendingIntent`、`initialMessage`、`initialSent` 一致性：任何路径确认受理都完成首条消息的收尾；失败只回退发送标记，不能丢失待确认意图。

对于刷新恢复，已受理运行从服务器恢复，不自动再发送。若保留未知提交的重试能力，需要把最小待确认意图按会话保存在当前标签页状态中，恢复时复用原键；不保存 Cookie 或 API Key。身份或会话权限已失效时清理该待确认状态，不能跨身份恢复。

取消接口返回的 `cancelRequested=true` 只表示请求已登记；终态必须以运行状态确认。队列中取消、执行中取消、取消与完成竞争均使用同一语义。旧 SSE 事件不得将已终态的运行重新变成生成中。

编辑草稿、发送、取消是三个独立能力。允许等待期间编辑下一条草稿，同一会话仍只受理一个活动运行。请求取消失败时保留实际运行状态，不能假装已经停止。

<a id="progress"></a>
## 5. 实际执行状态的展示

当前 SSE 类型为 `AI_THINKING / AI_EXECUTING / AI_GENERATED_CONTENT / AI_DONE`，`AI_PLANNING` 仍是预留能力。执行事件还包含模型、重试、工具、检索、持久化与错误。

| 可确认的信号 | 合适的文字 |
| --- | --- |
| 请求发出但尚未确认受理 | 正在提交问题 |
| 摘要为 QUEUED | 正在等待处理 |
| AI_THINKING，尚未取得检索结果 | 正在分析问题 |
| 明确知道 KnowledgeTool 正在执行 | 正在检索资料 |
| 只有通用 AI_EXECUTING | 正在执行操作 |
| 已取得检索结果，又进入模型阶段 | 正在整理回答 |
| 请求取消已登记 | 正在取消 |
| SSE 断开 | 连接中断，正在恢复 |
| 服务器确认为终态 | 按成功、失败、取消或中断显示 |

只有从真实返回中才能显示「找到 N 段资料」。如果现有事件不足以表达具体阶段，可新增兼容的可选阶段字段，并由实际执行节点发送；同步携带 runId，使客户端能够丢弃其他运行或已结束运行的迟到事件。

计时器只能显示「已等待多久」，不能推进虚构进度或百分比。排队耗时、执行耗时来自服务端；浏览器观察的等待时长另行标注。AI_DONE 表示流程结束，成功与否仍结合终态，不一律显示「回答成功」。

<a id="citations"></a>
## 6. 引用与原文

来源只取服务端核验后写入的 `metadata.citations`。保留现有 `AnswerCitation`：label、source、excerpt，以及可选的 citationId / 索引信息。

- 展示层可以按 `documentId + sourceHash` 分组，保留各个不同的位置和片段。重复检索得到同一出处可以收拢展示，但完整记录仍可查看。
- 分组不重新赋予模型正文中的编号含义。普通 Markdown 链接或模型随手写出的 `[1]` 不能自动变成受信来源按钮。
- 默认显示少量文档入口和准确的片段计数；展开后查看全部来源，不能静默丢掉模型实际引用的依据。
- 原文访问复用受权内容接口，不拼接磁盘路径。行号和 hash 遵守现有 `SourceText` / 引用契约。
- 新版索引应提供可靠的 sourceHash、startLine、endLine；旧来源缺位置时打开整份文档并解释。
- 发现当前内容与来源 hash 不一致时，说明资料版本已变化，不把旧行号当作精确证据；不得临时模糊搜索一段文本后声称哈希已核验。
- 文案用「查看依据」或「来源可核对」。来源身份与位置经过校验，不代表答案事实已经被自动判定正确。

本批以紧凑来源入口和准确定位完成闭环。若进一步实现逐段答案绑定引用，需增加明确的结构化关联协议并做服务端验证，不能靠正则推断每句话属于哪条来源。

<a id="reading-position"></a>
## 7. 阅读位置

| 事件 | 滚动行为 |
| --- | --- |
| 用户主动发送新问题 | 显示新问题和本轮状态 |
| 首条完整答案到达，用户仍跟随本轮 | 让答案开头处于可读视口，避免跳到末尾来源 |
| 用户上滚阅读旧内容、选择文本或展开来源 | 保持当前位置 |
| 阅读旧内容期间有新回答 | 提供查看新回答的入口，不强制跳转 |
| 展开来源/执行详情、异步加载、窗口改变 | 保持当前阅读锚点，正常允许内容增高 |
| 用户点击查看新回答 | 跳到该答案开头 |
| 打开历史会话 | 保持合理的最近一轮阅读起点；不用展开的来源把答案挤出视野 |

实现时区分用户滚动与程序定位，并在内容变化前判断是否跟随当前运行。不要只依赖新增消息数量和渲染后距底部多少像素。

<a id="data-version"></a>
## 8. 数据版本和发布

- 原三份公开资料是 v1 冻结资产，保持原始字节。v2 使用新增目录和独立 manifest，新增 LF 规则。
- manifest 只列入允许上传的正文；提示词、题集、验收和开发文档不被目录扫描带入。
- 新 KB 经真实上传、解析、Embedding 和索引发布后才可切入公开 Agent 的检索范围。文档版本、索引版本和模型绑定都要记录。
- 最终切换保留现有公开 Agent ID；涉及配置文件时核对是否需要重启以及实际生效值。
- 旧 KB 可继续服务历史引用，但不参与新的默认检索；不要先删除旧资料再重建。
- 回答范围以新公开资料和最新事实为准，公开内容准确区分继承能力、本仓库新增和仍未验证的部分。
- 演示样例来自真实执行并明确只读。查看样例不应触发模型请求，亲自体验才创建个人运行。

<a id="streaming"></a>
## 9. 后续流式输出的进入条件

本节是后续协议要求，不能当作已经存在的 API。

在 UX-05 数据支持流式改造后，先写 ADR，明确至少这些字段与行为：

1. 每段输出所属的 runId、答复 ID 与递增序号，重复事件可去重。
2. 正在生成的部分文本与已提交正式答案的区别；完成事件包含最终持久化消息 ID。
3. `directAnswer` 工具参数尚不完整时，不能把半段 JSON 当成答案；引用也只有通过校验后才能进入可信来源层。
4. 取消、租约丢失或被接管后停止后续推送，已终态不能被迟到增量重新激活。部分内容保持「未完成」语义，不升级为成功答复。
5. 最终答案仍走同一受租约与 fencing 保护的事务写入路径；不能为了降低延迟绕过守卫。
6. 重连按已持久化状态恢复，不自动重新执行结果未知的模型调用；明确是否支持增量重播，不承诺未实现的断点续传。
7. 保持发送幂等、取消跨心跳周期、任务间心跳隔离、摘要有界等锁和写后复查的已有回归。

在这些行为明确并通过验证前，第一批采用实际状态反馈和短答优化。不得把模拟进度或播放完整答案的动画计作流式性能成果。
