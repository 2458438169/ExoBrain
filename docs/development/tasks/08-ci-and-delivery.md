## 基础 CI

1. 使用 Java 21、仓库 Maven Wrapper、Node.js 22 和 `npm ci`。构建应可在干净 clone 中运行，不依赖开发者本机的 dev 配置和上传目录。
2. 把确定性单元测试、真实 PostgreSQL 集成、真实模型实验分开。基线 `JchatmindApplicationTests` 与 `agent/examples/*Test` 启动完整 Spring 上下文，不能假定默认 `mvn test` 已经完全离线。
3. 真实模型示例可改为显式 tag/profile；默认检查仍须包含功能/权限单测与必要集成。不要删除测试、全局 skipTests、忽略失败或使用动态排除让零测试也变绿。
4. PostgreSQL 集成使用兼容的 pgvector/PostgreSQL 17 临时容器、随机测试凭据和独立上传目录，安装基线加所需迁移；验证应用角色权限，不只用 postgres 超级用户跑所有 SQL。
5. 模型协议用本机确定性 stub 或等价夹具验证，常规 PR 检查不请求真实收费服务。真实语义评测单独显式运行，无凭据时清楚标记未运行，不能回退假指标。
6. 运行前端 lint、TypeScript 构建；游客与账号双构建都检查，不能只在根路径构建一次。
7. 浏览器测试使用合成账号/文档，覆盖登录与退出、普通用户管理入口限制、私有资源隔离、公开只读、预览、删除、引用、刷新恢复及 390px 移动端。选择少量关键流程，避免无意义的截图快照堆积。
8. 工作流按最小权限使用只读仓库 token，避免为外部 PR 注入秘密或在有写权限的上下文执行不可信 PR 代码；CI 不顺带自动部署生产。
9. 产物保存测试摘要、失败日志和合成截图，设有限保留期。过滤 Cookie、登录请求体、密钥、私有语料，不能通配打包本机配置目录。
10. 给出一个实际存在的统一检查入口；CI 与本地使用相同脚本，不能只在文档列出尚未实现的命令。

基线部署说明当前使用一组明确的 Maven 测试选择器。重整测试标签/profile 时核对覆盖的类和数量，不能为了改成简短命令丢掉已有权限、删除、模型和 SSE 测试。

## 双构建契约

下列命令是当前前端构建方式，CI 中使用等效的隔离环境配置；从 `ui/` 执行：

~~~powershell
npm ci
npm run lint

$env:VITE_PUBLIC_DEMO = 'true'
$env:VITE_API_BASE_URL = '/api/demo'
$env:VITE_SSE_BASE_URL = '/sse/demo'
npm run build -- --base=/ --outDir=dist-public

$env:VITE_PUBLIC_DEMO = 'false'
$env:VITE_API_BASE_URL = '/admin/api'
$env:VITE_SSE_BASE_URL = '/admin/sse'
npm run build -- --base=/admin/ --outDir=dist-admin
~~~

`VITE_*` 是编译时配置，修改运行容器环境不能改变已构建页面。05/06/07 新增路径要对照 Nginx 正则逐条验证，不能把公开接口的严格白名单替换成全量放行。

## 工程文档

- 根 README 写已可用的产品行为、技术入口、快速开始和清晰限制，链接架构/评测/部署文档。**不要恢复已移除的冗长验证结果段落。**
- `docs/architecture.md` 说明实际请求链路、身份校验、索引发布和执行恢复边界；架构图不能把尚未实现的队列、重排或模型降级画成已存在。
- 每个关键 ADR 包含问题、考虑过的方案、最终选择、代价、验证与何时重新评估。至少覆盖正文切块/版本化、来源身份与位置、权限在后台传播；第二阶段再补任务幂等与副作用恢复边界。
- `docs/provenance.md` 明确保留上游来源/许可证，把原有 Think-Execute/工具框架与新增账号隔离、模型管理、可核验来源等按真实差异说明。不是用 GitHub 贡献者列表替代来源说明，也不改写历史。
- 02 的公开评测报告包括原始逐题结果、样本量、失败例、运行配置和局限。不要只挑通过案例，不用“企业级”“高准确率”等未经证实的宣传。
- 发布 03 后，更新公开说明中标题索引/top3/固定分段的事实；旧库仍未重建时区分新旧行为。评测语料作为冻结版本保留，不随 README 更新悄悄改动。
- 产品公开页面/精选只展示正常资料与真实问答，不把开发任务、调参答案、内部身份或凭据上传到知识库。

## 每批集成检查

1. 收集各 Agent 的基线、提交和 delivery，核对协议版本与迁移顺序；按指南中的共享文件顺序集成，冲突逐项理解后解决。
2. 先跑相关检查，再跑实际发布版本的必需回归。测试环境的报告不能冒充线上验证；每份结果带 commit 和构建标识。
3. 权限矩阵最少覆盖两个普通用户、管理员、两个游客：私有目录/文档/检索/引用/执行记录/任务状态/写操作，以及所有新 API 的越权请求。
4. 数据生命周期覆盖现有数据保留、文件预览、原子删除、文件清理重试、模型绑定。新旧索引与后台任务存在时不能删库后复活。
5. 若当批包含发布职责，先核实实际环境和当前 release，完成备份、迁移、应用角色授权、两份前端与网关的候选验证，再按已获授权发布。
6. 记录回滚的可执行步骤，尤其是索引代际切换和新旧 worker 不得同时执行。不要盲目再次运行之前已执行过的一次性部署脚本。
7. 发布后核验游客入口、账号登录、普通/管理权限、私有隔离、MD 预览/引用、当前任务状态及服务日志；只清理可证明由测试创建的资源。
8. 根文档和部署记录与实际发布匹配，再把准确提交推送到用户的 ExoBrain 远程。先核实 remote，不推向上游，不强推覆盖其他提交，不添加未要求的 coauthor trailer。

## 完成标准

干净环境按文档能执行有实际覆盖的检查，CI 失败会真实失败；读者能分清已实现功能、待实现方案和实测结论。交付记录列出本批提交、构建、测试通过/失败/跳过/未执行、迁移与部署状态；没有负责或执行上线时明确写“未部署”，不把任务完成等同于生产完成。
