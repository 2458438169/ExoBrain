# ExoBrain 优化开发指南

本指南把优化拆成职责明确的开发任务，目标是让知识回答有可核验的来源、检索效果有可复现的指标、后台执行有明确的恢复边界。推荐由一位主 Agent 自行调用子 Agent 完成实现与审查，并统一集成交付。

**文档基线：2026-10-16，提交 `212a17ce19315e6cd8c88e5d77258a87c20b10fa`。下列任务均为待实施方案，不代表功能已经上线或指标已经达到。** 领取任务时记录自己的实际起始提交；若相关代码已变化，先检查差异，不覆盖后续成果。

## 1. 如何分发

**用户只需发送[主 Agent 开发交接单](orchestrator.md)中的启动提示词。** 主 Agent 自主分派、跟进和验收子 Agent，承担最终集成、回归、文档与 GitHub 推送职责。任务 08 可交给子 Agent 实现，最终发布负责人仍是主 Agent。

主 Agent 读取本指南、[共享契约](contracts.md)和全部任务书；每个子 Agent 读取总约定、自己的任务书及前置交付。任务书开头的独立提示词可作为子任务素材，工作目录、基线、文件权限与 Git 规则由主 Agent 补全。

1. 先分发 **01、02、08 的基础部分**，三者可以独立开始。
2. 01 合入后实施 03；02 应先留存旧检索基线，再用同一批资料比较 03。04 可根据共享契约先做界面与契约测试，最终联调依赖 03。
3. 第一阶段到 **01 + 02 + 03 + 04 + 08 的集成验收**为止，形成“资料导入 → 检索 → 回答 → 引用原文 → 效果对比”的完整能力。
4. 第一阶段通过后，主 Agent 继续分发和完成 05、06、07。用户交办全部任务时，阶段验收是检查点；用户限定了阶段范围时按其要求执行。第二阶段任务可分别交付，不以全部完成为第一次发布的前提。
5. 主 Agent 管理共享文件、验收和发布。独立工作区由子 Agent 按授权提交；共用目录时明确文件所有权，并由主 Agent 统一暂存、提交与集成，不能相互执行 reset、clean 或覆盖未提交修改。

按依赖和环境容量调用子 Agent，不要求额外搭建调度系统。已获用户授权的操作沿用既有授权；本指南不新增确认流程。子 Agent 默认交付代码和证据，由主 Agent 统一推送主分支并处理已授权的迁移与部署；用户另行指定职责时以用户要求为准。

## 2. 任务目录与优先级

| 编号 | 任务书 | 关键交付 | 前置条件 | 阶段 |

| 06 | [持久化文档导入](tasks/06-durable-ingestion.md) | 异步索引、失败重试、重启恢复、删除竞态处理 | 03 索引发布机制稳定 | 第二阶段 |

## 4. 所有任务必须遵守的产品边界

- **私有资源按账号隔离，管理员也无权访问其他账号的私有知识库、助手与会话。** 新接口、后台任务、来源引用、执行记录与评测入口都受同一边界约束。管理员保留用户管理、系统 LLM / Embedding 模型管理、公开资源管理能力。
- 保留游客免登录与账号登录。游客仅访问发布白名单中的资料和自己的访客会话；普通用户对公开演示资源只读；新知识库默认私有。
- 权限必须由服务端核验，不能依靠模型提示词、隐藏按钮、客户端传入的 userId/kbId 或前端过滤。后台工作线程不得冒用管理员身份或假设请求线程的身份自动存在。
- 保留 MD 预览/源码切换、当前 2 MiB 预览限制、历史会话 Agent 关联、删除后的聊天保留语义。没有准确来源位置的旧记录要降级显示，不能补造引用和执行数据。
- 删除不能留下可检索的索引或“复活”的后台任务。保留事务后文件清理与重启重试，沿用规范资源 ID、路径边界和不跟随符号链接的保护。
- 模型目录和密钥机制继续使用。相同的 1024 维不等于相同向量空间；已有 KB 的模型绑定不得静默切换，部署不得重新生成已有加密密钥。
- 页面保持正常知识助手产品表达。公开示例必须来自实际执行、可公开的资料；不放入准备过程、内部身份、凭据、调试日志或人为编造的成功轨迹。评测答案与开发文档不进入知识库。
- 保留上游 [JChatMind](https://github.com/youngyangyang04/JChatMind) 来源与 [MIT 许可](../../LICENSE)。如实区分继承能力和本仓库新增能力，不重写历史来掩盖来源，不添加用户未要求的协作者署名。

[共享契约](contracts.md) 是本批工作的初始约定，**并非已有 API**。生产者实现前把必要修订写入契约并通知消费者；不能仅在自己的分支改变字段名。消费者用合成夹具开发，交付前必须跑真实后端联调。

建议新领域能力放入职责清晰的 `retrieval/`、`execution/` 或 `ingestion/` 包/模块；这些是建议新增位置，基线中尚不存在。不要顺带进行全仓重命名、格式化或架构替换。

每位 Agent 的交付记录放在拟新增的 `docs/development/deliveries/<任务编号>.md`，包含：实际基线 SHA、完成范围、修改文件、接口/迁移、执行过的命令、真实结果、未覆盖事项和后续依赖。没有执行的验证写“未执行”及原因，不写“通过”。

各任务的 ADR 使用带任务编号的独立文件名，08 维护目录索引；共享测试夹具由生产者先提交，消费者复用同一份，避免自行定义不同的 hash、行号或状态语义。

## 6. 一次可接受的第一阶段交付

必须能够在隔离测试环境完成以下过程，并留下可复现证据：

1. 两个普通账号分别导入不同的合成文档；并发处理没有串文。管理员也不能检索、引用或预览其中任何不属于自己的私有资料。
2. 询问“正文包含、标题没有”的事实，命中正确片段；回答引用能打开对应文档并定位原文。无匹配、服务失败、已删除来源有不同反馈。
3. 对固定语料和问题集运行旧检索与新检索，报告逐题命中、Recall@k / MRR@k、资料不足表现和耗时；保留失败案例。结果不理想也如实交付，不硬凑提升比例。
4. 游客和登录用户都能完成真实问答；刷新后仍能看到有权访问的历史及来源。普通问候不需要伪造工具调用；依赖实时工具的问题只能使用实际执行结果。
5. lint、类型检查、构建、相关后端测试、真实 PostgreSQL 集成与双模式浏览器检查通过。公开记录只包含明确允许发布的资料。
6. README 描述与实际功能一致；基线的“标题向量索引”说明只有在相关库完成迁移后才更新。新建库与未重建旧库行为不同时必须写清。

根 README 保持产品与技术入口简洁，不重新加入已经移除的冗长验证结果段落。逐项验证放在交付记录、评测报告和部署说明。

## 7. 集成与发布约定

- 先合并依赖、核对共享契约，再测试实际待发布的提交。不能把不同分支的测试结果拼成一个版本的“全部通过”。
- 不重放旧的一次性部署脚本。由实际环境检查决定迁移、应用角色授权、后端镜像、游客/账号两份前端与 Nginx 白名单是否需要一起更新。
- 数据库迁移必须增量、可复核；不要改写已应用的迁移，也不要向已有库重新执行带默认数据的初始化脚本。新索引先构建验证后切换，失败保持旧索引可用。
- 发布前留存数据库、上传文件、模型密钥和原发布版本的可恢复备份；敏感材料留在仓库外。回滚旧应用前核验它能否读取新结构，不能只回滚 JAR 却留下不兼容索引。
- 此仓库的推送目标是 `https://github.com/2458438169/ExoBrain.git`。当前本机远程名为 `exobrain`，`origin` 指向上游；其他机器先验证映射再推送。不要强推覆盖其他 Agent 的工作。
- 文档任务本身不触发生产升级。以后发布实现时沿用用户对该任务的授权，由指定负责人完成，不重复索要已经给过的许可。
