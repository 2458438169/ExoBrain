## 2. 数据模型与状态迁移

`exobrain_run`（摘要）：

- `id`、`schema_version = 1`、`session_id`→`chat_session`（`ON DELETE CASCADE`）、`triggering_message_id`→`chat_message`（`ON DELETE SET NULL`）、`answer_message_id`→`chat_message`（`SET NULL`）、`agent_id`→`agent`（`SET NULL`）。
- 快照：`agent_name_at_start`、`agent_config_hash`（SHA-256，只存哈希）、`model_catalog_id`、`model_name_at_start`。
- `status`（六态，`CHECK`）、`origin`（`ACCOUNT/DEMO`）、`submitted_at`、`started_at`、`finished_at`、`duration_ms`、`queue_duration_ms`、`input_tokens`、`output_tokens`、`total_tokens`、`error_code`、`trace_incomplete`、`heartbeat_at`。
- 约束：耗时/用量非负；终态必须有 `finished_at`；`finished_at >= started_at`。

`exobrain_run_event`：`id`、`run_id`（`CASCADE`）、`sequence`、`type`、`status`、`started_at`、`duration_ms`、`tool_call_id`、`tool_name`、`retrieval_id`、`retry_attempt`、`error_code`、`detail`（≤200 的受控标签）；`(run_id, sequence)` 唯一，负耗时被拒绝。

状态迁移规则：

| 场景 | 结果 |
| --- | --- |
| 正常完成（有答复） | `RUNNING → SUCCEEDED`，`durationMs` = 进程内单调时钟真实耗时 |
| 达到步数上限 | `RUNNING → SUCCEEDED` + `STEP_LIMIT` 事件（不是失败，但明确记录） |
| 模型/工具/落库抛错、上游繁忙重试耗尽 | `RUNNING → FAILED` + `ERROR` 事件，`errorCode` 为固定码（`MODEL_UNAVAILABLE`/`EXECUTION_FAILED`/`MESSAGE_PERSISTENCE_FAILED`…） |
| 会话/账号授权撤销 | `RUNNING → FAILED`，`errorCode = AUTHORIZATION_REVOKED`；不发任何迟到 SSE |
| 流程结束但从未产出面向用户的答复 | `RUNNING → FAILED`，`errorCode = NO_ANSWER_PRODUCED` |
| 重启遗留的 `RUNNING` | 数据库不改写；读取时心跳超过 `app.execution.stale-run-seconds`（默认 300 秒）返回 `INTERRUPTED` + `interrupted = true` |
| 迟到的 `RUNNING`/另一个终态更新 | 拒绝（0 行）；同终态重复写入幂等（1 行） |
| 主记录创建失败 | 不执行；账号发“执行记录创建失败，本次请求未执行”，游客返回 503 |
| 中途事件写入失败 | 保留已写事件、置 `trace_incomplete`、WARN 一条，不补造事件 |

`RunTracingExecutionTest` 用 04 引入的 `requestModel` 脚本化边界回放真实执行循环（工具执行、落库前 DTO、事件记录都走生产实现），8 个场景：

1. 正常（检索 + 答复）：事件序列 `MODEL_CALL, PERSIST_MESSAGE, TOOL_CALL, RETRIEVAL, PERSIST_MESSAGE, MODEL_CALL, PERSIST_MESSAGE, TOOL_CALL, PERSIST_MESSAGE`——每个真实调用恰好一条事件；`KnowledgeTool` 与 `directAnswer` 各自带自己的 `toolCallId`；检索事件带 `retrievalId=ret-1`、`detail=OK`；所有耗时 ≥ 0；sequence 唯一且连续；每次事件都刷新心跳；最终答复消息与运行关联；消息 metadata 带服务端 `runId`；无用量时为 null。
2. 普通问候：只有 `MODEL_CALL` + `PERSIST_MESSAGE`，没有任何工具事件。
3. 工具失败：`TOOL_CALL` 为 `FAILED/TOOL_FAILED`，执行继续并真实完成第二次模型调用。
4. 两次重试后成功：attempt 依次 1/2/3，前两次 `FAILED/UPSTREAM_BUSY`，第三次 `SUCCEEDED`；运行耗时包含真实退避（≥3000 ms）。
5. 达到步数上限：20 次模型调用 + 20 次工具事件 + 1 条 `STEP_LIMIT`（无 `toolCallId`）。
6. 授权撤销：撤销后不再写“已完成”的工具/落库事件，异常向上抛。
7. 无答复结束：`state() == ERROR`，不关联答复消息，运行时不伪造错误事件（由调用方分类）。
8. 用量累加：11/5 + 7/3 → 18/8/26；未提供时保持 null。

`RunModelTest`：状态机（终态不可被迟到更新覆盖、同终态幂等）、用量（全 0/全空 = 未提供、按字段累加、负数被拒）、事件写入失败（保留已有记录、`sequence` 仍消耗、标记不完整、不抛异常）。

### 3.5 测量开销（结构性计数，不是压测）

一次“检索 + 答复”的账号运行在脚本化回放里产生 9 条事件 → 9 次事件 INSERT + 9 次心跳 UPDATE + 1 次运行 INSERT + 1 次终态 UPDATE + 1 次答复关联 UPDATE ≈ 21 条语句。**没有做吞吐/延迟压测，也没有 QPS 或 P95 数字**，因此不声称开销可忽略。

## 5. 敏感字段与脱敏

- 不存储、不返回：API Key、令牌/哈希、Cookie、内网地址、完整助手配置快照、提示词全文、模型私有推理文本、工具参数、其他用户的文档/片段。
- 助手配置只存 `agent_config_hash`（SHA-256，输入含名称/描述/提示词/模型/工具/知识库/参数），用于“同一配置”比对。
- 事件 `detail` 只放受控短标签（如检索状态 `OK`/`NO_MATCH`/`UNAVAILABLE`、`MAX_STEPS_20`），不写模型文本。
- 错误只保留固定分类码；不写服务商原始异常。日志只含 `runId`、事件类型与异常类名。
- SSE metadata 只新增 `runId`（服务端生成），不含配置或凭据。
- 公开精选投影（`RunViews.PublicSummary/PublicEvent`）不含 `sessionId`、`triggeringMessageId`、`answerMessageId`、`agentId`、`agentConfigHash`、`modelCatalogId`、`toolCallId`、`retrievalId`、`eventId`；集成测试对序列化 JSON 做了断言。
- 公开精选的消息 metadata 仍由 `DemoCatalogService` 白名单生成（不含 `runId`），05 没有扩大公开字段。

## 6. 给 07（持久化对话任务）的接口

- **运行状态存储**：`RunRepository.create(RunSummary)` / `findById` / `findBySessionId(sessionId, origin)`；表 `exobrain_run` 增列即可扩展排队字段，不要改 `status`/`origin`/`duration_ms` 语义。
- **事件追加**：`RunRepository.appendEvent(RunEventRecord)`（`sequence` 由 `RunRecorder` 单调分配，`(run_id, sequence)` 唯一）；执行侧的 `RunRecorder` 可继续复用，`attachRun` 即可接入新流程。
- **幂等终态更新**：`RunRepository.complete(runId, status, finishedAt, durationMs, usage, errorCode, traceIncomplete)`；SQL 条件 `status IN ('QUEUED','RUNNING') OR status = target`。07 的“崩溃时标记 `INTERRUPTED`”直接调用 `complete(..., INTERRUPTED, ..., "INTERRUPTED_BY_RESTART", ...)`；读取层已把心跳过期的 `RUNNING` 呈现为 `INTERRUPTED`（`RunQueryService.interrupted`），07 接管后可以改为持久化。
- **错误分类**：`RunLifecycleService.classify(Throwable)` 与 `RunLifecycleService.failed/succeeded` 可直接复用。
- **扩展位置**：`QUEUED` 状态与 `queueDurationMs` 已在表/视图里预留；新增“领取者/租约/尝试次数”请加独立列与语句，`submittedAt` 已取触发消息落库时间（`chat_message.created_at`），排队耗时可继续用它计算。
- **注意**：`RunRecorder` 的事件写入失败只置 `trace_incomplete`；07 若要“终态必须落库”，需要自己检查 `complete` 返回 0 行的情况（05 只记 WARN）。
