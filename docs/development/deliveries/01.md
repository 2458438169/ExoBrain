## 2. 并发安全依据（不是仅凭 final 字段推断）

- flexmark-all **0.64.8**，本地 `~/.m2` 只有二进制包，因此核对的是 jar 内字节码而不是源码注释。
- `com.vladsch.flexmark.parser.Parser` 实例字段均为 `final`，`parse(String)` / `parse(BasedSequence)` / `parseReader(Reader)` / `postProcess` 中只有 `getfield` 读取，没有 `putfield`，也没有 `monitorenter`。
- 但 Parser 持有的配置 `DataHolder` 在首次解析时会把“计算出的默认值”写回自身：一次 `parse` 之后 `parser.getOptions()` 会多出 `DataKey<EmptyList> SPECIAL_LEAD_IN_HANDLERS`，写回目标是普通 `java.util.HashMap`（`MutableDataSet.getOrCompute`），没有任何同步。
- 结论：共享同一 `Parser` 会让并发解析同时写同一张 `HashMap`，官方也没有线程安全承诺，因此改为**每次调用新建 Parser**（本机实测构建约 0.063 ms/次，可接受）。配置与请求状态都不跨调用共享，单次调用的可变状态（DocumentParser、Document 及其引用仓库）由 flexmark 在 `parse()` 内部按调用创建。
- 未使用 static 字段、共享 ThreadLocal，也没有给整个服务加 `synchronized`。

## 3. 表格分支可达性

基线构造器未注册任何 extension，因此 GFN 风格表格文本目前按普通段落解析，`TableBlock` 分支**不可达**；`MarkdownParserServiceImplTest.productionConfigurationNeverBuildsTableBlockNodes` 用真实 AST 遍历确认生产配置下不会出现 `TableBlock`。启用 `TablesExtension` 会改变解析行为（表格章节内容从纯文本变为原始表格 Markdown），属于需要单独评估的变更，本任务不做。

- 并发样本：16 份互不相同的合成 Markdown × 5 轮 = 80 次解析，单轮耗时约 44 ms（合计 220 ms）。
- 每份样本在标题、正文、表格、代码块带唯一标记，断言逐份检查“自己的标记都在、别人的标记都不在”，并核对标题序列与章节数。
- 覆盖：40/1/8 行填充的不同长度、CRLF（样本 M10）、重复标题（`index % 4 == 0`）、中文、空输入（样本 M15）、表格文本、代码块。
- 并发起跑由 `CyclicBarrier` 控制并设置 30 s 等待上限，取结果 60 s 上限，失败信息包含轮次与样本编号。
- 4 个 skipped 与本次改动无关：是 `DocumentStorage*Test` 在 Windows 上无法创建符号链接的既有跳过。
