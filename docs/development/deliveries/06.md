## 2. 状态机、租约/fencing 与重试策略

- 状态：`QUEUED → RUNNING → SUCCEEDED`；临时失败 `RETRY_WAIT` → 重新领取；超过 `max_attempts`（默认 3）`FAILED`；
  资源/权限变化 `CANCELLED`。**成功 = 03 的新 revision 已 `PUBLISHED`**，上传 200 只代表“已受理”。
- 领取：一条语句 `WITH candidate AS (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1) UPDATE … RETURNING`，
  取到期的 `QUEUED`/`RETRY_WAIT` 或租约过期的 `RUNNING`；每次领取 `attempts+1`、`fencing_token+1`、写 `lease_owner/lease_expires_at`。
- fencing：`renew / succeed / finish / retryLater` 全部带 `AND fencing_token = ? AND status='RUNNING'`（续租还要求租约未过期）。
  领取后被别人接手的旧 worker 一次写回都不会成功；runner 在 `LEASE_LOST` 时**不写任何状态**。
- 发布闸门（`IngestionPublisher`，`@Transactional`）：`SELECT … FOR UPDATE` 锁任务行 → 核对 `status/fencing_token/lease_owner/租约`
  → 复核 KB、文档、账号、KB 归属 → 比对源 hash（任务提交时记录的 hash）→ `RetrievalIndexService.publish`（03 在同一事务里
  再核对文档清单/基础版本/模型绑定并原子切换）→ 写 `SUCCEEDED` 与 `index_revision_id`。任一步失败整体回滚，旧索引保持可用。
- 解析与 Embedding 在事务外；每完成一个 chunk 续租并写 `chunks_done`（真实进度，`chunks_total` 由切块结果写入）。
- 退避：`min(base·2^(n-1), max)`，默认 30s 起、600s 封顶。分类：
  - 可重试 `EMBEDDING_UNAVAILABLE / INDEX_CONFLICT / FILE_UNREADABLE / PUBLISH_FAILED`
  - 永久失败 `EMBEDDING_REJECTED / MODEL_UNAVAILABLE / MODEL_DISABLED / NOT_INDEXABLE / TOO_MANY_CHUNKS / FILE_CHANGED /
    FILE_TOO_LARGE / UNSUPPORTED_TYPE / ATTEMPTS_EXHAUSTED / PUBLISH_REJECTED / INTERNAL_ERROR`
  - 取消 `DOCUMENT_DELETED / KNOWLEDGE_BASE_DELETED / ACCOUNT_DISABLED / NOT_AUTHORIZED`
- 资源检查不是“开始时一次”：worker 开始、每次续租、发布事务内都重新检查；文档/KB 删除会级联删除任务行，
  旧 worker 的后续写回与发布都会失败。

### 4.3 必做故障注入逐项结论

| 注入点 | 实际做法（真实 PG，不是 mock repository） | 结论 |
| --- | --- | --- |
| 文件已写、DB 提交前崩溃 | 集成：`orphanSweeperRemovesOnlyCrashedUploads` 在库里没有文档行的 UUID 目录写文件并回退 mtime 3h；单元：`orphanIsRemoved/existingDocumentIsKept/referencedJobIsKept/freshDirectoryIsKept/foreignDirectoriesAreSkipped`；上传事务回滚由 `failedJobInsertRollsBackAndRemovesSavedFile`/`unreadableFileIsNotAccepted` 覆盖 | 孤儿被删除；有文档行、有任务引用、宽限期内、非 UUID 目录、KB 已删除的目录都**不动** |
| DB 提交后、worker 启动前重启 | `committedJobIsReclaimedAfterRestart`：worker-a 领取后租约过期，worker-b 重新领取（attempts=2，fencing_token+1）；worker-a 的 `finish` 返回 false | 任务可重新领取；旧租约写不回终态 |
| Embedding 暂时失败 / 永久错误 | `transientEmbeddingFailureRetriesThenSucceeds`（502 → `RETRY_WAIT`/`EMBEDDING_UNAVAILABLE`，0 chunk，无 revision；到期后重试 → `SUCCEEDED`，chunk 数 == `chunks_total`）；`permanentEmbeddingErrorFailsWithoutIndex`（400 → `FAILED`/`EMBEDDING_REJECTED`，无 chunk、无 `DRAFT` revision） | 有限重试 / 明确终态，两次都没有半成品可检索 |
| 两个 worker 竞争同一任务 | `twoWorkersRaceForOneJob`：8 个并发 `claim`，只有 1 个拿到（`fencing_token=1`），其余为空 | 一个有效发布者 |
| 构建中删除文档或 KB | `documentDeletedDuringBuildPublishesNothing`（第一次 embed 时删文档）：任务行随文档消失、旧 revision 仍 `PUBLISHED`、旧 chunk 仍在、新文档 0 chunk；`knowledgeBaseDeletedDuringBuildPublishesNothing`（第一次 embed 时删 KB）：任务/索引/chunk 全为 0，之后 `runOne()` 领取为空 | 结果不发布、不复活已删资源 |
| 构建中改变账号状态或停用模型 | `disabledAccountCancelsWithoutEmbedding`：`CANCELLED`/`ACCOUNT_DISABLED`，0 chunk，无 revision（embedding 未被调用）；`disabledModelFailsWithoutPublishing`：`FAILED`/`MODEL_UNAVAILABLE`，0 chunk | 按定义取消/失败，不越权 |
| 索引发布事务失败 | `publishRejectedKeepsOldIndex`：切块后插入另一份文档使候选清单过期 → `RETRY_WAIT`/`INDEX_CONFLICT`，旧 revision 仍唯一 `PUBLISHED`，新文档 0 chunk；移除干扰文档后同一任务到期重试 → `SUCCEEDED` | 旧索引保留；首次导入失败可恢复 |
| 用户重复点击重试 | `duplicateRetryClicksKeepSingleJob`：4 个并发 `retry` 全部解析到同一 jobId；库里该文档只有 1 行任务、1 个活动任务；重试成功后 chunk 数 == `chunks_total` | 不生成并行任务或重复 chunk |

另外 `submittedJobIsIndexedAndPublished` 断言：成功后活动 revision 为 `PUBLISHED`、chunk 均带 revision（无 legacy 行）、
`chunks_done == chunks_total`、任务不可再次领取；`statusViewIsSafe` 断言状态 DTO 不含存储路径。

### 4.5 验证过程中发现并修掉的两个真实缺陷

1. **`RETRY_WAIT` 无法被重新领取**：领取语句最初只匹配 `QUEUED`，重试任务会一直停在 `RETRY_WAIT`。
   集成测试 `transientEmbeddingFailureRetriesThenSucceeds` / `publishRejectedKeepsOldIndex` 第二次 `runOne()` 返回 false 暴露了它；
   已把 `RETRY_WAIT` 加入领取条件。
2. **错误分类与终态不匹配**：`IngestionErrorCode` 的 `cancelling` 标志最初把永久失败码写成“取消”、把资源删除码写成“失败”，
   导致 `ACCOUNT_DISABLED` 落到 `FAILED`、`FILE_CHANGED` 落到 `CANCELLED`。单元测试 `IngestionJobRunnerTest` 修正后一对一验证。

## 5. 删除、并发与孤儿清理结论

- 删除文档：`DocumentFacadeServiceImpl.deleteDocument` 仍是“同一事务删行 + 入 `StorageCleanupService` 队列 + 刷新活动版本计数”；
  导入任务行由 `ON DELETE CASCADE` 一起消失，worker 的续租/发布复核因此必然失败，**不会复活**。
- 删除 KB：`KnowledgeBaseFacadeServiceImpl` 未修改（不在本任务改动范围），任务/文档/chunk/索引都由外键级联清理；
  已验证删除后没有任何任务、revision 或 chunk 残留。
- 文件清理仍只由 `StorageCleanupService`（`exobrain_storage_cleanup`）负责；导入队列没有插入该表的任何一行。
- 孤儿清理只处理“数据库里从未存在过”的文件：需要同时满足规范 UUID 两级目录、KB 存在、无文档行、无任务引用、
  超过宽限期；删除时逐层校验真实路径并拒绝符号链接/目录联接。KB 级目录与非 UUID 名字一律跳过。
- 同一 KB 的并发上传：后到的候选会被 03 的发布校验拒绝（`INDEX_CONFLICT`），任务到期重建候选即可，不会把新文档
  放进一个永不发布的版本里。

## 6. 03 接口的复用方式与偏离

复用（未修改 `retrieval/**` 任何文件）：

- `RetrievalIndexService.resolveScope(kbId)`：判断该 KB 是 `legacy-title-v1` 还是 `body-v1`。
- `RetrievalIndexService.prepareDocument(kbId, source)`：切块（不写库、不调外部服务）。
- `RetrievalIndexService.publish(candidate)`：在发布闸门的事务内调用，因此加入同一事务，原子切换。
- `LegacyTitleIndexer.index(...)`：legacy 库保持基线行为（标题向量、无 revision、无位置）。
- 03 的竞态校验（文档清单、基础版本、模型绑定、KB 行锁）保持不变，`INDEX_CONFLICT` 就是它们的拒绝信号。

唯一的偏离：**没有调用 `embedCandidate`**，而是在 runner 里逐 chunk 调用 `ModelRuntimeService.embed`。
原因是要在 chunk 之间续租并上报真实 `chunks_done`，同时能在续租失败时立刻停止（`embedCandidate` 是一次性循环，
无法插入这两个动作）。两者逻辑等价（逐 chunk 调同一个 `runtime.embed`），发布仍完全走 03 的 `publish`。
对 03 的接口没有任何修改请求。

## 7. 给 07（持久化对话任务）可参考的领取测试与模式

- 领取写成**一条语句**（`WITH candidate AS (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1) UPDATE … RETURNING`），
  既不需要长事务，也天然多实例安全。07 的队列表建议同样形状，但**不要**复用 `exobrain_ingestion_job`。
- `fencing_token`：每次领取 +1，所有写回都带 `AND fencing_token=? AND status='RUNNING'`；租约过期后旧持有者一个字节都写不回。
  运行态还需要“`INTERRUPTED` 只由恢复流程设置”，可以参考本任务的“租约过期 → 重新领取”测试。
- 测试模式（可直接抄）：
  - `IngestionJobIntegrationTest.twoWorkersRaceForOneJob`：N 线程 `CountDownLatch` 同时领取，断言只有 1 个成功、token=1；
  - `committedJobIsReclaimedAfterRestart`：领取 → 手动把 `lease_expires_at` 推回过去 → 另一 owner 领取 → 断言旧 token 写回失败；
  - `@BeforeEach` 里清空本任务队列表，避免上一个用例遗留的到期任务被先领取（我踩过这个坑）；
  - 故障注入用“可切换的引用 + 一次性钩子”（见 `embedFailure`/`embedHook`），不要在同一个 mock 上反复
    `when(...).thenThrow(...)`——第二次打桩会真的抛出上一次的异常。
- 07 应保留“运行记录 ≠ 断点续跑”的表述；本任务只承诺领取/租约/恢复，不承诺 exactly-once 外部调用。

## 10. 未执行项与限制

1. **不提供 exactly-once**：worker 崩溃后任务会被重新领取，已经发生的 Embedding 调用不会回滚，可能重复付费。
   只保证最终发布不产生重复 chunk（新 revision + 唯一索引 + 原子切换）。
2. **崩溃恢复的粒度是一次完整执行**：没有 chunk 级断点续跑，重试会重新切块并重新向量化整份文档。
3. **没有取消/优先级 API**：`CANCELLED` 只来自资源删除、账号停用与权限撤销；管理员无法手动中止一个正在跑的导入。
4. **legacy 库不升级**：`legacy-title-v1` 库的异步导入仍写 legacy 行（无 revision、无位置），进度里的 chunk 数是 legacy 行数；
   想要正文检索必须先显式重建（任务 03 的 `rebuild`），本任务不会自动切换。
5. **进度只到 chunk 粒度**：`chunks_total` 在切块完成后写入；在此之前只能看到阶段（界面不显示百分比）。
6. **没有优雅停机等待**：进程退出时正在执行的任务会等租约过期后被重新领取（默认最多 120s 的等待 + 退避）。
7. **未测量吞吐/时延**：没有做导入吞吐或上传响应时间的基准测量，因此不给出任何性能数字或收益结论。
8. **未执行**：真实浏览器双模式交互检查；多进程/多主机（只验证了同库多 worker 线程与独立 `IngestionWorker` 实例）。
