## 2. 队列、幂等与租约

- 提交：用户消息、固定历史快照与排队任务在**同一事务**里写入；返回 `runId` + `runStatus=QUEUED`（重复提交同一幂等键返回原 message/run 并带 `idempotentReplay=true`）。JVM 事件只是唤醒提示，进程重启后仍由 `exobrain_chat_run_job` 恢复。
- 幂等：`(actor, session, key)` 唯一约束；相同键不同内容按设计拒绝；不按问题文本去重。
- 领取：worker 短事务领取（`FOR UPDATE SKIP LOCKED` 风格），带租约与 fencing；模型调用不占数据库事务；每个检查点续租，租约丢失抛 `RunLeaseLostException`，旧 worker 不能写回终态。
- 边界：全局 `max-queued`、每身份 `max-active-per-actor`、并发执行上限、幂等键长度上限；超过即拒绝，不把数据库当无限缓存。
- 授权：每次开始与关键步骤重新走 `ResourceAccess` / 运行守卫；账号停用、会话撤销、助手或知识库权限变化、模型停用都不会因已入队而绕过。
- 状态：`QUEUED / RUNNING / SUCCEEDED / FAILED / CANCELLED`（+ 05 的中断语义 `INTERRUPTED`）；终态幂等且不可被迟到事件覆盖。
- 副作用：不自动重放未知结果的外部调用；运行中取消是协作式停止，已发出的外部请求可能无法撤回。**不承诺 exactly-once。**

## 6. 未执行项与限制（重要）

1. **队列场景已补齐自动化验证**（`jchatmind/src/test/java/com/kama/jchatmind/integration/RunQueueIntegrationTest`，真实 PostgreSQL，**13 项全部通过**）：
   - 幂等键：同一 `(actor, session, key)` 重复插入被数据库拒绝；同键换会话或换身份视为不同提交意图；`findByIdempotencyKey` 只返回原来那一行；
   - 同会话单活动运行：第二条活动任务被部分唯一索引拒绝；进入终态后会话槽位释放；
   - 领取与 fencing：`claim` 置 RUNNING、`attempts+1`、`fencing_token+1` 并写租约；只领取 QUEUED（RUNNING 或已取消的不会被二次领取）；`renew` 只接受当前 fencing，旧 fencing 被拒；
   - 租约过期 → 中断：`interruptExpired` 把过期 RUNNING 置 `INTERRUPTED`（`INTERRUPTED_BY_RESTART`，运行摘要同步），旧 worker 用旧 fencing 写终态被拒绝，重复中断不会二次生效；**有活租约的任务不会被其它实例中断**；
   - 取消：排队中原子终止（`CANCELLED_BEFORE_START`）且幂等；运行中只写协作式停止请求、行保持 RUNNING，随后 `renew` 失败；取消后写入完成只留下一个终态，再写 SUCCEEDED 被拒；
   - 重启：新的 repository 实例仍能从数据库领取 QUEUED（fencing 0→1），已完成的运行不会被重放。
   - 自动化测试未覆盖的：真正的进程重启、并发 HTTP 提交、`idempotentReplay` 响应分支的端到端验证（运行中撤销授权后的队列行为由 `AuthExecutionReauthorizationTest` 在运行层覆盖）。**这三项已在 2026-10-18 用两个真实 JVM 进程补做**，见 `docs/development/deliveries/durable-runs-drill.md`。
2. **多实例**：2026-10-18 已用两个独立 JVM 进程 + 同一数据库实测（A/B 分别领取并完成不同运行、同会话并发一个 200 一个 409、幂等键重放返回同一 `runId`、`kill -9` 后由存活实例标记 `INTERRUPTED` 且不重放）。**仍未验证多主机/网络分区/时钟漂移**，见 `durable-runs-drill.md` 第 4 节。
3. **租约与模型时延**：演练把 `lease-seconds` 压到 20 s 时，出现存活实例自己的运行被过期扫描判为 `INTERRUPTED`（单次模型调用超过租约）。默认 120 s 下 3/3 冒烟通过；结论与建议记录在 `durable-runs-drill.md` 第 2 节，代码未改。
4. **真实浏览器**：2026-10-18 已补做（时间线、排队/运行状态、引用按行定位、SSE 断线刷新），见 `docs/development/deliveries/browser-acceptance.md`。

### 8.1 F01（P1）运行已中断，过期 worker 仍可写入最终答复

- 根因：终态写回有 fencing，但普通消息 INSERT 没有；运行被标 `INTERRUPTED` 之后，落库路径仍能成功。
- 修复：
  - 新增 `runs/RunResultWriter`：一个短事务内 `SELECT … FOR UPDATE` 锁任务行 → 校验 `fencing_token` 与
    `status='RUNNING'` → 写消息 → 仅在终态可达时写 `answer_message_id`；任一步不满足整笔回滚并抛
    `RunLeaseLostException`（迟到答复一个字都不留）。
  - `RunRepository` 增加 `setAnswerMessageIdIfRunning`（`WHERE status='RUNNING'`），旧的无条件版本保留给历史路径。
  - `JChatMind.attachRunPersistence(...)`：运行上下文下所有消息（含最终答复）都走上面的守卫；没有运行上下文
    （单元测试/演示）时退化为原行为。
  - `RunLease` 增加**独立心跳**（`startHeartbeat`/`close`，间隔 = 租约/3，只做一次短 UPDATE）：模型调用期间也续租，
    避免「仍活着的运行被过期扫描误判为中断」（这正是演练里 20 s 租约 + 长模型调用出现过的现象）。
  - `RunWorker.runNow` 启动/结束时开关心跳；`RunLease.finish` 先停心跳再写终态。
- 回归：`integration/RunResultGuardIntegrationTest`（真实 PostgreSQL，5 项）——终态后迟到答复被拒且零消息、
  正常答复与关联在同一事务、fencing 被接管后旧 worker 写不进、心跳能挡住过期扫描、同键重放取回原运行。

### 8.2 F02（P1）前端未接入幂等键

- 修复（`ui/src/components/views/AgentChatView.tsx`、`ui/src/api/api.ts`）：
  - 每次「新的发送意图」生成一个稳定键（`crypto.randomUUID()`，降级随机串），失败重试与 SSE 重连后的首条消息恢复
    都**复用同一个键**；只有服务端确认受理（返回 `chatMessageId`/`runId`）后才结束该意图。
  - 不按问题文本去重：用户有意重复提问仍会创建新运行。
  - 请求/响应类型补齐 `idempotencyKey`、`runId`、`runStatus`、`idempotentReplay`。
- 实测（真实 Chromium + 真实后端）：用 `fetch` 包装器让首次 POST **照常到达服务端**但把响应丢掉，页面出现
  `Failed to fetch` 且草稿保留；再次点击发送后，浏览器发出两次提交但**同一个幂等键**，数据库里仍是 1 个运行、
  1 条用户消息、1 个任务 `attempts=1`、1 条模型答复。

### 8.3 F03（P2）同键并发重试参数顺序错误

- 根因：`RunSubmissionService.replayAfterConflict` 调 `findByIdempotencyKey(actorScope, normalizeKey(key), sessionId)`，
  而签名是 `(actorScope, sessionId, key)`，同键并发重试因此查不到原行并误报 409。
- 修复：改为 `(actorScope, sessionId, normalizeKey(key))`。
- 回归：`RunResultGuardIntegrationTest.replayAfterConflictUsesSessionAndKeyInOrder` —— 同键同内容返回原 `runId`
  且 `replay=true`；同键不同内容仍抛冲突（不会被旧运行冒充）。

### 8.4 F04（P2）无 assistant 消息的终态运行在刷新后不可见

- 修复（`ui/src/components/views/agentChatView/AgentChatHistory.tsx`）：
  - 运行列表按 `triggeringMessageId` 建索引，**没有 `answerMessageId` 的运行**直接挂在对应提问下面，显示状态
    （排队中/执行中/成功/失败/已取消/中断）、`errorCode`、耗时与 runId 短标识，并按状态给出可读说明。
  - `QUEUED/RUNNING` 的运行单独 5 s 轮询（不再依赖消息条数变化），刷新或 SSE 断连后仍能看到终态。
- 实测：真实取消（`POST /api/runs/{id}/cancel` → `CANCELLED_BY_USER`，无 assistant 消息）与真实中断
  （`INTERRUPTED_BY_RESTART`）两个会话，刷新后都显示「本次回答 / 已取消（或 状态未知）/ 错误码 / 耗时 / 运行 id」。
