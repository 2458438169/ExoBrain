## 7. 过程中发现并修复的缺陷（真实运行暴露，已加离线回归）

1. **Embedding 请求被 Cloudflare 拒绝**：urllib 默认 `Python-urllib/3.7` UA 得到 `HTTP 403 / error code: 1010`；显式发送 `User-Agent: ExoBrain-Eval/0.1 (+…)` 后返回 200/1024 维。修复在 `exo_runtime.py`（`EMBEDDING_USER_AGENT`）。
2. **hit 元数据全部为空**（第一次真实运行 Hit@1/3 = 0.000）：`chunk_bge_m3.content/metadata` 列类型是 TEXT，psql 侧 `to_json(col)::text` 是**双重编码**，`json.loads` 一次只得到字符串，`metadata` 退化成 `{}` → `docKey/startLine/endLine` 全为 `None`，命中判据全部失败。修复为 `decode_json_column` 两级解码，并加 `tests/test_runtime_parsing.py` 回归；修复后同一索引、同一题集得到第 5 节的真实数字。
3. **`summary.byCategory` 恒为空**：`build_summary` 把 `scopes`（题目 ID 集合）当 `split` 传给 `category_breakdown`，所有题被过滤掉。修复并加回归断言。

**索引不是 Python 重实现的切块**：语料经产品上传接口进入导入队列，由 `IndexPublisher` 用
产品自身的 `BodyChunker` 切块、用产品配置的同一个 Embedding 端点建向量，评测端只读 SQL。

### 12.1 索引与被测环境

- 一次性隔离库 `exobrain_eval02`（容器 `exobrain-dev-pg`，PostgreSQL 17.11 + pgvector 0.8.7），
  按 `db/jchatmind.sql` → `20261014-accounts` → `20261014-models` → `20261016-storage-cleanup` →
  `20261017-03` → `20261017-05` → `20261017-06` → `20261017-07` 顺序应用（19 张表）。
- 应用用已提交的 jar（`git rev-parse HEAD = e6a2da5` 构建产物，`jchatmind-0.0.1-SNAPSHOT.jar`）
  以外部配置启动，`app.embedding` 指向 `https://emrank.tech/v1` + `BAAI/bge-m3`（1024 维）。
- 4 份冻结语料（含 `synthetic-eval-only` 干扰文档）经 `POST /api/documents/upload` 上传，
  逐份等待导入任务 `SUCCEEDED`（6 + 12 + 18 + 23 次分块，最后一版 revision 共 23 个 chunk，
  4 份文档）。合成文档只写入这个一次性评测库，**没有**进入应用库、公开演示环境或产品文档。
- 发布结果：`exobrain_index_revision` 中 `status = PUBLISHED`、`chunk_count = 23`、
  `document_count = 4`、`source_set_hash = 37dbb922…`、`revision_id = 7b69ef54-…`；
  `exobrain_kb_index_state.active_index_version = body-v1`。快照见
  `evaluation/runs/body-v1/index-snapshot.json`，切块清单见 `evaluation/runs/body-v1/chunks.csv`。
- 四个文档分别导入会各自发布一版 revision（前 3 版被 `SUPERSEDED`，旧 chunk 行保留），
  因此适配器必须按 `active_revision_id` 过滤，否则 top-k 会混进旧版本片段。

### 12.2 为跑通对比而修的三处适配器问题（都有离线回归）

1. **只按 KB 过滤不够**：产品的检索 WHERE 是「KB + 当前 PUBLISHED revision」，适配器新增
   `useActiveRevision`（`evaluation/scripts/exo_runtime.py`），改为按
   `exobrain_kb_index_state.active_revision_id` 过滤。
2. **产品元数据没有 `docKey`**：03 写的是 `documentName`（原始文件名），`docKey` 是 02 的标注键。
   新增 `docKeyFromDocumentName`：按冻结 manifest 的文件名唯一映射，重名直接报错、缺映射标
   `scorable=false`，不猜、不模糊匹配。
3. **`metadataLike` 的空格匹配不到真实行**：`run-config.example.json` 里写的
   `%"indexVersion": "body-v1"%` 带空格，而产品写入的是紧凑 JSON（`"indexVersion":"body-v1"`），
   按它过滤会得到 `INDEX_NOT_FOUND`。示例配置改为使用 `useActiveRevision` + `docKeyFromDocumentName`。

新增离线用例 `evaluation/tests/test_body_v1_adapter.py`（7 条）覆盖：文件名映射、重名报错、
docKey 解析、缺映射不可评分、revision 过滤开关、`make_strategy` 接线。

### 12.4 差距归因（诊断，不替代冻结指标）

`evaluation/scripts/diagnose_boundaries.py` 把 44 个 required 证据单元逐条分类
（`evaluation/runs/body-v1/boundary-diagnostic.json`）：

| 运行 | 冻结覆盖单元 | boundary-only | facts-missing | partial-overlap | no-hit-in-doc |
| --- | --- | --- | --- | --- | --- |
| legacy-title-v1 | 34 / 44 | 0 | 0 | 6 | 4 |
| body-v1 | 26 / 44 | **17** | 0 | 0 | **1** |

结论：

- 第 3 节判据要求“单个片段完整包含 gold 行范围”，而 03 的切块**把章节标题行排除在正文之外**，
  标题改由元数据 `headingPath` 承载，并裁剪首尾空行。44 个单元里有 17 个以标题行作为 `startLine`，
  这些单元在 body-v1 下**结构上不可能**被单个片段“完整包含”（例：q003 gold 5–9，产品 chunk 为 7–9，
  正文与三条事实都在）。
- 把这 17 个单元改成“覆盖去掉首尾标题/空行后的正文窗口”后，body-v1 覆盖 43/44 个单元、
  40/40 道有答案题（诊断口径），而 legacy 仍是 34/44、34/40。真实检索缺口只有 1 个
  （q022：`java-backend-faq` 25 行没进 top-3）。
- 因此：**按当前冻结判据，body-v1 的 Hit/Recall/MRR 低于基线；差距几乎全部来自判据与切块边界的
  结构性冲突，而不是检索质量下降**。dev 集 MRR 反而小幅提升、干扰片段命中率显著下降，
  与“正文索引减少标题语义干扰”的预期一致。

### 12.5 结论与建议（未擅自改冻结口径）

- 冻结判据与题集**不做任何修改**，本文与 `README` 只陈述两种口径的真实数字；对外汇报必须同时
  写明“0.600 是标题行判据下的值”。
- 若要给 02/03 一个可比较的正式口径，建议由后续任务**重新冻结**一版判据：命中要求
  「正文窗口被覆盖 + 事实字符串在 payload 内 + 标题由 `headingPath` 单独校验」，并同步更新
  `freeze.json`（重新冻结后旧基线必须重跑，不能拿旧数字直接比）。
- 该判据变更涉及 02 的冻结资产，本轮**未执行**，留待明确授权。
